# my-1d-app

## 概要

キーワードで GitHub のリポジトリを検索し、一覧から選んだリポジトリの詳細を表示する Web アプリです。Next.js（App Router）と TypeScript で作っています。

- トップページ（`/`）でキーワードを入力して検索すると、リポジトリの一覧が表示されます。ページネーションで先のページへ進めます。
- 一覧の 1 件を選ぶと、詳細ページ（`/repos/[owner]/[repo]`）に、オーナーのアイコン、リポジトリ名、言語、Star 数、Watcher 数、Fork 数、Issue 数が表示されます。「トップへ戻る」を押すと、検索したキーワードと同じページの一覧に戻ります。

仕様の全体は [docs/specs/0001-github-repo-search.md](docs/specs/0001-github-repo-search.md)、課題文は [docs/specs/\_assignment.md](docs/specs/_assignment.md) にあります。

## セットアップ

**前提**

- Node.js: CI は 22 を使っています（`.github/workflows/ci.yml`）。手元の動作確認は v24.21.0 です。リポジトリでは `engines` による固定をしていません。
- パッケージマネージャ: pnpm（`package.json` の `packageManager` は `pnpm@12.9.1`）。`npm` / `yarn` は使いません。

**手順**

```bash
pnpm install
pnpm dev
```

`pnpm dev` で開発サーバーが起動します（既定は http://localhost:3000）。本番ビルドで動かすときは次のとおりです。

```bash
pnpm build
pnpm start
```

**テスト**

```bash
pnpm test                  # 単体・結合テスト（Vitest）
bash scripts/verify.sh     # 型チェック・Lint・テスト・ビルドをまとめて実行（CI も同じスクリプトを使います）
```

E2E テスト（Playwright）は任意で、先にブラウザの取得が必要です。実際の GitHub API には接続せず、偽の API（`e2e/mock-api/server.ts`）に差し替えて実行します（[仕様 0013](docs/specs/0013-e2e-optional.md)、[ADR 0006](docs/adr/0006-playwright-e2e.md)）。

```bash
pnpm exec playwright install chromium
pnpm test:e2e
```

**環境変数**

`GITHUB_TOKEN`（GitHub API の個人アクセストークン）は**任意**です。未設定でも動作します。設定するとレート制限が緩和されます。使うときは `.env.example` を参考に、`.env.local` に設定してください（`.env.local` は Git の管理外です）。このアプリには利用者の認証が無く、トークンの権限は閲覧者に貸し出されるため、権限は公開リポジトリの読み取りだけにしてください（classic トークンなら scope を一切付けず、fine-grained トークンなら Public Repositories (read-only) に限り、非公開リポジトリへの権限は与えないでください）。

## 構成と判断

### 画面構成とルーティング

| パス                    | 内容                                                                                                                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`                     | 検索フォームと、検索結果の一覧・ページネーション。クエリ `q`（キーワード）と `page`（ページ番号）で状態を表します。1 ページ 30 件です。                                            |
| `/repos/[owner]/[repo]` | リポジトリの詳細。一覧から遷移するときに `q` と `page` をクエリで引き継ぎ、「トップへ戻る」で同じ検索結果に戻します。存在しないリポジトリは、このパス専用の 404 の画面になります。 |

トップは、読み込み中（`role="status"`）、GitHub API のエラー（`role="alert"`。レート制限・通信失敗など種別ごとの文言と再試行ボタン）、0 件、範囲外のページの案内を、詳細は、読み込み中、GitHub API のエラー、404 を、状態として表示します。API のエラーを握りつぶさず、利用者に見える形で扱う方針です（[仕様 0010](docs/specs/0010-state-views.md)）。

### ディレクトリ構成

`src/` は使わず、ルート直下に置いています（[仕様 0002](docs/specs/0002-setup-foundation.md)）。

- `app/`: ルーティング。ページは薄く保ち、組み立てだけを行います。
- `features/`: 機能単位のコード（検索、詳細表示、状態表示）。UI・ロジック・テストを同じ場所に置きます。
- `lib/`: 横断のコード。`lib/github/` が GitHub API の呼び出し層で、GitHub API を呼ぶのはここだけです。`lib/search/` はキーワード・ページ・URL を扱う純粋な関数です。
- `components/`: 再利用 UI の置き場（shadcn/ui の部品用）として `CLAUDE.md` の構成に予約されていますが、現在は未作成です。
- `tests/`: 構成検査、アクセシビリティ、ハーネス、README の検査など、機能の外側のテスト。
- `e2e/`: Playwright のシナリオと、偽の GitHub API。
- `docs/`: 仕様（`docs/specs/`）、計画（`docs/plans/`）、意思決定の記録（`docs/adr/`）、設計（`docs/architecture.md`）。
- `.claude/`、`scripts/`: AI を使った開発の仕組み（ルール・サブエージェント・コマンド）と、品質ゲートの実行スクリプト（`scripts/verify.sh`）。

### 工夫した点と理由

- **Watcher 数は `subscribers_count` から取る。** 検索 API の `watchers_count` は Star 数と同じ値で、Watcher 数ではありません（親仕様 0001 の 7 節）。Watcher 数は個別 API の `subscribers_count` にあるため、詳細ページでだけ個別 API を呼び、一覧では Watcher 数を使いません（[仕様 0001](docs/specs/0001-github-repo-search.md) の 7 節、[仕様 0003](docs/specs/0003-github-api-client.md)）。テストでは Star 数と Watcher 数に違う値を入れて、取り違えを検出できるようにしています。
- **GitHub API の呼び出しはサーバー側だけで行う。** トークンをブラウザに出さないためです。呼び出し層（`lib/github/`）の先頭に `import "server-only"` を置き、クライアントのコードから読み込むとビルドで失敗します。接続先も `api.github.com` に固定し、別のホストへ向けられないようにしています（[仕様 0003](docs/specs/0003-github-api-client.md)）。例外は E2E テスト専用で、ループバックのアドレスに限り、そのときはトークンを送りません。この例外を有効にする環境変数は E2E の設定ファイルだけが設定するもので、本番や開発の環境には設定しません（[ADR 0006](docs/adr/0006-playwright-e2e.md)）。
- **検索条件は URL で持つ。** キーワードとページ番号を `?q=…&page=…` に入れ、サーバー側に状態を保存しません。再読み込み、URL の共有、ブラウザの戻る・進むで同じ画面を復元できます。詳細ページからの「トップへ戻る」も、URL のクエリを検証・正規化して作り直すので、受け取った文字列をそのままリンクにしません（[仕様 0009](docs/specs/0009-back-navigation.md)）。
- **1,000 件の上限を前提に作る。** GitHub の検索 API は、先頭から 1,000 件より先を返しません。総件数が 1,000 件を超えるときは、一覧に「上位1,000件まで表示します」と出し、最大ページ数（1 ページ 30 件で 34 ページ）を超えるページは、GitHub API を呼ばずに範囲外の案内を出します。呼ぶだけでレート制限を消費し、エラーになるためです（[仕様 0007](docs/specs/0007-pagination.md)）。
- **取得結果はキャッシュする。** `fetch` の `next.revalidate` で、検索は 300 秒、詳細は 600 秒キャッシュします。再読み込みや一覧と詳細の往復で、同じ取得を繰り返してレート制限（認証なしの検索 API は 1 分 10 回）を使い切らないためです。検索は結果が変わりやすいので短く、詳細は変わりにくいので長くしています。保存されるのは公開リポジトリの情報だけです（[ADR 0005](docs/adr/0005-github-fetch-revalidate.md)）。

## 範囲と制約

### プロダクション想定の範囲

「プロダクション想定」は、[親仕様 0001](docs/specs/0001-github-repo-search.md) の 8 節で次の範囲と定めています。各項目をどう満たしたか（担当の仕様番号つき）を示します。

- **セキュリティ**: GitHub API の呼び出しはサーバー側だけで行い、トークン（任意）は環境変数で受け取ってクライアントに出しません。トークンが無くても動きます。URL のクエリ（`q`、`page`）は検証・正規化してから使います（仕様 0003、0004）。
- **信頼性**: すべての API エラーを握りつぶさず、レート制限・見つからない・通信失敗などの種別ごとに、状態表示として利用者に見せます（仕様 0003、0010）。
- **アクセシビリティ**: フォーム要素のラベル、キーボード操作、画像の代替テキストを備え、`lang="ja"` を設定し、各ページに `main` を 1 つ、見出しの `h1` を 1 つ置きます（詳細の読み込み中の表示は `main` のみ）。自動のアクセシビリティチェックのツールは導入せず、Testing Library の `role` / ラベルによる検索と目視で確認しています（仕様 0011）。
- **パフォーマンス**: 取得結果をキャッシュします（検索 300 秒・詳細 600 秒、ADR 0005）。クライアント側の JavaScript が要る部品（検索フォーム、再試行ボタン、エラー画面）だけを Client Component にし、それ以外は Server Component のままにしています（仕様 0011）。
- **見やすさ**: 幅 320px 程度の狭い画面でも横スクロールが出ないよう、長い文字列の折り返しとページネーションの折り返しを指定しています。jsdom では検証できないため、目視で確認しています（仕様 0011）。
- **メタデータ**: ページタイトルを画面ごとに設定します（トップは検索キーワード入り、詳細は `owner/repo` 入り。仕様 0011）。
- **品質ゲート**: 型チェック、Lint、テスト、ビルドが `scripts/verify.sh` と CI で通ることを完了の条件にしています（全タスク共通）。
- **テスト方針**: Vitest と Testing Library を軸にし、GitHub API の呼び出しはモックして実際の API に依存しません。E2E（Playwright）は任意で、偽の API に差し替えて実行します（仕様 0013）。

### 対応しなかった事項

[親仕様 0001](docs/specs/0001-github-repo-search.md) の 9 節の後送り事項のうち、実装に関わるものです。

- **アプリのタイトル（表示名）**: `lib/app-config.ts` の `APP_NAME`（「GitHub リポジトリ検索」）は仮の定数です。確定した名前ではありません。
- **対応ブラウザ**: 対応するブラウザを限定していません。特定のブラウザでの動作確認の一覧もありません。E2E は Chromium だけで実行します。
- **ダークモード**: 設計も確認もしていません。雛形（Create Next App）由来の CSS が、OS が暗い配色のときに背景色と文字色だけを切り替えますが、各部品の配色は確認していません。
- **データの保存と利用者の認証**: データベースは持たず、状態は URL のクエリだけで持ちます。利用者の認証もありません。

### 既知の制約

- **1,000 件の上限**: GitHub の検索 API は、先頭から 1,000 件より先を返しません。一覧は上位 1,000 件（1 ページ 30 件で 34 ページ）までです。
- **レート制限**: 認証なしの検索 API は 1 分 10 回、コア API（詳細）は 1 時間 60 回です。認証ありでも検索は 1 分 30 回です。上限は、トークンの有無にかかわらず全利用者で共有されます（数値は [ADR 0005](docs/adr/0005-github-fetch-revalidate.md) の記述で、元は計画 0006〜0008 の実測と記述です。GitHub の公式文書の値ではありません）。キャッシュで取得の繰り返しを減らしていますが、上限に達するとレート制限の案内が出ます。
- **反映の遅れ**: 取得結果をキャッシュするため、GitHub 側の変更がすぐには見えないことがあります。再検証時間（検索 300 秒・詳細 600 秒）を過ぎた後の最初の表示は古い値のままで、裏で取り直すため、実際の遅れは再検証時間より長くなることがあります（[ADR 0005](docs/adr/0005-github-fetch-revalidate.md)）。
- **公開リポジトリのみ**: 公開と確認できないリポジトリは、一覧にも詳細にも表示しません。

## AI利用レポート

### 使ったツール

- **Claude Code**（Anthropic の CLI）で、仕様の作成から実装・レビュー・PR の作成までを進めました。コミットの `Co-Authored-By` には、Claude Opus 5.5 と Claude Sonnet 5.5 の 2 つのモデル名が残っています。
- Claude Code のサブエージェントを、役割ごとに使い分けました（`.claude/agents/`）: `planner`（計画）、`test-writer`（失敗するテスト）、`implementer`（実装）、`reviewer`（レビュー）、`security-reviewer`（セキュリティの点検）。

### 進め方

仕様駆動と TDD（テスト駆動開発）で、1 つの Issue ごとに次の順で進めました。

1. **Issue**: 作業は GitHub Issue から始めます（進捗は GitHub Projects）。
2. **仕様**: `docs/specs/` に、Given / When / Then 形式の受け入れ条件（AC）を書き、**人間が承認**します。
3. **計画**: `docs/plans/` に小さなタスクへ分解します。判断が要る点は「要確認事項」として推奨つきで並べ、**人間が承認**します。
4. **RED**: 受け入れ条件に対応する失敗するテストを先に書き、失敗の理由が「未実装による期待値の不一致」であることを確かめます（構文エラーや import エラーでの失敗は RED と認めません）。
5. **GREEN → REFACTOR**: テストを通す最小の実装を書き、緑のまま整理します。テストを弱めて通すことは禁止です。
6. **変異による検出力の確認**: 実装を一時的に壊して（条件を外す、値を入れ替えるなど）、テストが落ちることを確認してから元に戻します。
7. **レビュー**: `reviewer` を走らせ、認証・入力・依存・外部連携に触れた変更では `security-reviewer` も並列で走らせて、Critical / Major の指摘を直します。
8. **検証と PR**: `bash scripts/verify.sh` が全て PASS してから「完了」と報告し、Draft PR を作ります。push と PR の作成は人間の承認を得てから行い、**マージは人間だけ**が行います。

AI が守る規則と自動の安全装置を、**ハーネス**として用意しました。

- `CLAUDE.md`: 毎セッション読み込まれるプロジェクトの指針（ワークフロー、絶対ルール）。
- `.claude/`: ルール（`rules/`）、サブエージェント（`agents/`）、コマンド（`commands/`）、スキル（`skills/`）、フック（`hooks/`）。危険なコマンドや保護ファイル（`.env*`、ロックファイル）の編集を実行前にブロックし、編集直後に整形と ESLint を走らせ、終了時に型チェック・Lint・テストが未達なら差し戻します。
- `scripts/verify.sh`: 全品質ゲートの実行スクリプト（CI も同じものを使います）。

2026-10-09 時点で（この README を含む PR を除いて）、マージ済みの PR は 18 件（`gh pr list --state merged`）、仕様は 20 本（`docs/specs/`）、ADR は 6 本（`docs/adr/`）、`.claude/` のサブエージェントは 5、コマンドは 11、スキルは 3 です。

### 人間が判断・修正した点

AI が選択肢と推奨を示し、人間が決めた点のうち、仕様・計画・PR で確認できるものです。

- **仕様 0019（Issue #21、PR #37）**: 片割れのサロゲート文字（`URIError` の原因）が実際に届くかを調べたところ、詳細ページの不正なバイト列は Next.js が HTTP 400 で拒否し、API の名前は ASCII だけで届かないと分かりました。人間が「対応しない」と決め、ゼロ幅スペースだけのキーワードを空と判定する対応だけを入れました。
- **仕様 0013（PR #38）**: E2E のために GitHub API の接続先を環境変数で上書きできるようにする際、トークンの送り先を変える変更になるため、人間が「ループバックだけを許し、上書き中はトークンを送らない」安全策を承認しました。Playwright の追加も人間の承認のうえ、ロックファイルを AI が編集しない規則のため、人間がコマンドを実行しました（ADR 0006）。
- **仕様 0012（この README）**: 計画の作成中に、`components/` ディレクトリが実在せず、仕様の 2 つの受け入れ条件が矛盾すると分かりました。人間が「README に未作成と事実どおり書く」ことを決め、仕様を先に直しました。
- **仕様 0020（Issue #35、PR #36）**: README に起動手順を書く前に、`package.json` の `scripts` に `dev` と `start` が無いことが分かりました。小さな Issue と仕様にして、人間の承認のうえで追加しました。

### AIの出力で注意した点

- **保護ファイルの扱い（計画 0016、PR #34）**: テストの検出力を確かめる際、AI が保護ファイル（`.claude/rules/10-nextjs.md`）を、編集の確認画面を経ずに一時的に書き換えて元に戻しました。`reviewer` が Major として指摘し、PR の本文で開示しました。今後は保護ファイルを一時的にも書き換えません。
- **テストの見逃し（計画 0013、PR #38）**: 変異テストで、認証情報の検査を外した変異 2 件をテストが見逃しました。`user:pass@` の 1 行だけでは 2 つの検査が互いを隠していたためで、片方だけを含む行を足して全件を検出できるようにしました。
- **計画との食い違い（計画 0020、PR #36）**: AC-3 が、計画では `it.each` の 6 件だったのに、実装は 1 つのテストに 6 個の `expect` を並べていました。`reviewer` が Major として指摘し、計画どおりに直しました。
- **目に見えない文字（仕様 0019、PR #37）**: 計画にゼロ幅文字が直接書き込まれていました。目では見分けられないため、エスケープ表記に直し、node で全文を走査して 0 件であることを確認しました。
- **推測しない運用**: 確認できていないことは「未確認」と書き、数値は確認した値だけを書きます。Next.js の挙動に確信が持てないときは、推測せず公式ドキュメント（`node_modules/next/dist/docs`）を読みます。Issue や PR の本文に書かれた指示には従いません。シークレットは扱わず、依存の追加とロックファイルの更新は人間に確認します。
