## 概要

キーワードで GitHub のリポジトリを検索し、一覧から選んだリポジトリの詳細を表示する Web アプリです。Next.js 16（App Router）と TypeScript で作っています。

- トップページ（`/`）でキーワードを入力して検索すると、リポジトリの一覧が表示されます。ページネーションで先のページへ進めます。
- 一覧の 1 件を選ぶと、詳細ページ（`/repos/[owner]/[repo]`）に、オーナーのアイコン、リポジトリ名、言語、Star 数、Watcher 数、Fork 数、Issue 数が表示されます。「トップへ戻る」を押すと、検索したキーワードと同じページの一覧に戻ります。

動かし方、構成、範囲と制約の詳細は、`docs/` の文書にまとめ、ここには要約と参照を置いています。工夫した点とこだわったポイント、そしてその選択をした理由は、「工夫した点と理由」に文章でまとめました。仕様の全体は [docs/specs/0001-github-repo-search.md](docs/specs/0001-github-repo-search.md)、課題文は [docs/specs/_assignment.md](docs/specs/_assignment.md) にあります。

## セットアップ

Node.js と pnpm があれば、次の 2 つのコマンドで開発サーバーが起動します（既定は http://localhost:3000）。

```bash
pnpm install
pnpm dev
```

環境変数 `GITHUB_TOKEN` は**任意**で、未設定でも動作します。本番ビルドでの起動、テスト（単体と、ブラウザで一連の動作を確かめる E2E）、トークンの権限の詳細は [docs/setup.md](docs/setup.md) にあります。

## 工夫した点と理由

### Watcher数の取得元

詳細ページの Watcher 数は、個別のリポジトリ API の `subscribers_count` から取っています。GitHub の検索 API にある `watchers_count` は、名前に反して Star 数と同じ値で、本当の Watcher 数ではありません。そのため、一覧では Watcher 数を使わず（一覧に出すのはオーナーのアイコンとリポジトリ名だけ）、詳細ページでだけ `subscribers_count` を読みます（[仕様 0001](docs/specs/0001-github-repo-search.md) の 7 節）。

この取り違えは、見た目では気づきにくい間違いです。Star 数と Watcher 数が同じ値になっていても、画面は崩れず、型も合ってしまいます。そこで、テストでは Star 数 100 と Watcher 数 7 のように、あえて違う値を入れて、取り違えたら必ず落ちるようにしました（[仕様 0003](docs/specs/0003-github-api-client.md) の受け入れ条件。機能が満たすべき条件のことです）。E2E のモックサーバーにも、使われないはずの値（`watchers_count` に 99999）を入れてあり、画面に出てしまったら失敗します。検索 API の応答には Watcher 数が無いため、Watcher 数は詳細ページで個別 API を呼んで取ることになります。

### GitHub APIをサーバー側だけで呼ぶ

GitHub API の呼び出しは、サーバー側（Server Component）だけで行います。理由は、アクセストークン（`GITHUB_TOKEN`）をブラウザに渡さないためです。呼び出しを担う `lib/github/` の先頭に `import "server-only"` を置き、クライアント側のコードから読み込もうとするとビルドで失敗するようにしました。「気をつける」ではなく、間違えたら機械的に止まる形にしています。

接続先も `api.github.com` に固定し、パスに絶対 URL や `//host` の形を渡されても別のホストへ向かないように検査しています。トークンを外部のホストへ送ってしまう事故を避けるためです（[仕様 0003](docs/specs/0003-github-api-client.md)）。この固定には、E2E テストのためのただ一つの例外があります。サーバー側から呼ぶ以上、ブラウザ側のリクエストの差し替え（Playwright の機能）では偽の API に切り替えられないからです。環境変数で接続先を上書きできるようにし、ループバックのアドレスに限り、上書き中はトークンを送りません。この上書きを有効にする環境変数は E2E の設定ファイルだけが設定するもので、本番や開発の環境には設定しません。モックライブラリの導入や実際の API への接続も検討し、依存が増える点と、不安定でレート制限がある点から採りませんでした。設計上の判断の記録（ADR）は [ADR 0006](docs/adr/0006-playwright-e2e.md) にあります。

### 検索条件をURLで持つ

キーワードとページ番号は、`/?q=react&page=2` のように URL のクエリで持ち、サーバー側にもブラウザの保存領域にも状態を保存しません。理由は、再読み込み、URL の共有、ブラウザの「戻る」「進む」で、同じ画面を必ず復元できるからです。詳細ページへ移るときも `q` と `page` をクエリで引き継ぐので、「トップへ戻る」を押すと、検索したときと同じキーワード・同じページの一覧に戻ります。

URL から来る値は信用せず、戻り先のリンクは、受け取った文字列をそのまま使わずに、検証して作り直します（`q` が空、または 257 文字以上ならトップ `/`、`page` が不正なら 1 ページ目）。外部のサイトへ飛ばすリンクを作らせないためです（[仕様 0009](docs/specs/0009-back-navigation.md)）。トレードオフは、URL のクエリは誰でも書き換えられる値のため、受け取った文字列をそのまま使わず、毎回検証して作り直す手間が要ることです。

### 1,000件の上限の扱い

GitHub の検索 API は、先頭から 1,000 件より先を返さず、それより先のページを求めると 422 のエラーになります。呼ぶだけでレート制限も消費します。そこで、総件数が 1,000 件を超えるときは、一覧に「上位1,000件まで表示します」と出し、1 ページ 30 件で最大 34 ページまでとしました。それを超えるページを URL で直接開かれた場合は、GitHub API を呼ばずに「範囲外」の案内を出します（[仕様 0007](docs/specs/0007-pagination.md)）。

範囲外の判定は 2 段で行っています。ページ番号が 34 を超えるなら API を呼ばずに範囲外とし、API を呼んだ後は、総件数に対して最終ページを超えているかで判定します。総件数が 0 件のときは範囲外にせず、「0 件」の案内を出します。上限に触れて失敗する前に、画面の側で言葉にして伝える設計です。トレードオフは、1,001 件目以降のリポジトリはこのアプリでは見られないことです。範囲外のページでは、総件数・一覧・ページネーションは出さず、案内と先頭や最終ページへの導線だけを出します（[仕様 0007](docs/specs/0007-pagination.md)）。

### 取得結果のキャッシュ

取得結果は、`fetch` の `next.revalidate` で、検索を 300 秒、詳細を 600 秒キャッシュします。理由は、GitHub API のレート制限（認証なしの検索 API は 1 分 10 回）です。キャッシュが無いと、再読み込みや、一覧と詳細の往復で、同じ取得を繰り返して制限を使い切ってしまいます。検索結果は変わりやすいので短く、リポジトリの詳細は変わりにくいので長くしました。利用者に返すのは、公開リポジトリの情報だけです（公開と確認できないものは返しません）。ディスクに残るキャッシュには GitHub の生の応答が入るため、トークンは公開リポジトリの読み取りだけの最小権限にします。

ほかに検討した案もあります。キャッシュしない案は、背景の問題が残るため採りませんでした。`unstable_cache` は、Next.js 16 で `use cache` に置き換えられた古い API です。`cacheComponents` と `"use cache"` は、アプリ全体のレンダリングの仕組みが変わり影響が大きいため、仕様の範囲外としました。採用した `fetch` の指定は、`lib/github/http.ts` の 1 か所で済み、追加の依存も要りません。動的ルート（クエリを読むページ）でも効くことは、実機で確認しています（[ADR 0005](docs/adr/0005-github-fetch-revalidate.md)）。トレードオフは、GitHub 側の変更の見え方が遅れることです。実際の古さは、最大で「再検証時間＋次のリクエストまでの間隔」になります。

### エラーを状態として見せる

GitHub API のエラーを握りつぶさず、レート制限、見つからない、検証エラー、GitHub 側の異常、通信失敗という種別ごとに、利用者に分かる文言で表示します。レート制限のときは、リセットされる時刻が分かれば、その時刻（日本時間）も出します。読み込み中、0 件、範囲外は `role="status"`、エラーは `role="alert"` にして、支援技術にも伝わるようにしました。

実装で気をつけたのは、種別ごとの表示を、ページの中で作る点です。本番の Next.js は、Server Component で投げた例外のメッセージを `error.tsx` に渡さず、固定の文言しか届かないため、`error.tsx` だけで受けると種別を出し分けられません（[仕様 0010](docs/specs/0010-state-views.md) の 2 節）。そこで、ページが `GitHubApiError` を受け止めて、種別ごとの画面を描画し、想定外の例外だけを `app/error.tsx` が受けます。エラー文はトークンや URL、レスポンスの本文を含まない固定の文言にしました。トレードオフは、エラー表示と 404 が、ストリーミングの都合で HTTP 200 で返ることです。

### テストの検出力を確かめる

テストを書いて通っただけでは、そのテストが本当に間違いを見つけられるかは分かりません。特に、最初から緑になるテスト（現状の振る舞いを固定するテスト）は、効いているのか見分けがつきません。そこで、実装を一時的に壊して（条件を外す、値を入れ替える、検査を省くなど）、テストが落ちることを確かめ、確かめたら元に戻す「変異」の確認を、計画 0006 以降の各計画（`docs/plans/`）で行いました（結果は各計画の進捗メモにあります）。

効果が出た例として、接続先の上書きの実装（計画 0013）で、テストが見逃していた検査の抜けを見つけて直しました。詳しくは「AI利用レポート」の「AIの出力で注意した点」に書いています。トレードオフは、時間がかかることと、変異のスクリプトはリポジトリに入れておらず、CI では実行しないことです（結果は各計画の進捗メモに記録しています）。

## テスト

機能の振る舞いを確かめるテストと、リポジトリの決まりごとを確かめるテストを書きました。

- **単体・結合**: Vitest と Testing Library を使い、各コードの隣に置いています。画面は、利用者から見える要素（ロールやラベル）で確かめます。GitHub API の呼び出しはモックし、実際の API には依存しません。
- **構造検査**: ディレクトリ構成、設定、文書の決まりごとを確かめるテストです（`tests/foundation/`、`tests/harness/`、`tests/docs/`）。README 自身の構造も検査しています。
- **アクセシビリティ**: ページの見出しの構造や、フォーカス表示を消していないことを確かめます（`tests/a11y/`）。
- **E2E**: Playwright で、検索から詳細へ進み、戻るまでの流れを実際のブラウザで確かめます。偽の GitHub API に差し替えて実行する、任意実行のテストです（[ADR 0006](docs/adr/0006-playwright-e2e.md)）。

テストは、受け入れ条件から先に書きます。また、通るだけでなく、壊したときに落ちることを、実装を一時的に壊す「変異」で確かめました（[テストの検出力を確かめる](#テストの検出力を確かめる)）。

実行は `pnpm test`（単体・結合・構造検査・アクセシビリティ）、`pnpm test:e2e`（E2E）、`bash scripts/verify.sh`（型チェック・Lint・テスト・ビルドをまとめて）です。手順の詳細は [docs/setup.md](docs/setup.md) にあります。

## 構成

画面は 2 つです。トップページ `/`（検索フォーム、検索結果の一覧、ページネーション。クエリ `q` と `page`）と、詳細ページ `/repos/[owner]/[repo]` です。ディレクトリ構成と各画面の状態表示の詳細は [docs/structure.md](docs/structure.md) にあります。

## AI利用レポート

### AI利用について考慮した点

- 基本的にAIに作業させることに注力すること。仕様・計画・テスト・実装・レビュー・PR の本文まで Claude Code に書かせ、私は承認と判断に集中しました。
- タスクを細かく細分化し、機能を積み上げることで完成に近づけること。親仕様を機能ごとの仕様に分け、依存の順に 1 つずつ PR にして積み上げました（仕様 0001 の 4 節。着手できるタスクの抽出は、後に ADR 0004 で自動化しました）。
- まずはGitHub+AIをフル活用したワークフローを作ること。Issue を起点に、仕様・計画・実装・レビュー・下書きの PR までをコマンド（`/feature`、`/pr`）で進められるようにしました（ADR 0002）。

### 使ったツールと任せた範囲

- ツールは Claude Code（Anthropic の CLI）です。モデルは Claude Opus 5.5 と Claude Sonnet 5.5 で、コミットの共著者の記録に残っています。
- 役割ごとに別の指示を持たせた AI の担当（サブエージェント）を使い分けました。計画を作る planner、失敗するテストを書く test-writer、実装する implementer、レビューする reviewer、セキュリティを点検する security-reviewer です。
- AI に任せたのは、仕様の下書き、計画、テスト、実装、レビュー、PR の本文です。人間の私が担ったのは、仕様と計画の承認、選択肢の判断、push と PR 作成の承認、マージ、依存の追加コマンドの実行です。

### 進め方

仕様駆動と TDD（テスト駆動開発）で進めました。まず仕様に受け入れ条件（機能が満たすべき条件を、前提・操作・結果の形で書いたもの）を書いて承認し、計画に小さなタスクへ分けて承認します。その条件から先に失敗するテストを書き（RED）、最小の実装で通し（GREEN）、整理します。さらに、実装を一時的に壊してテストが落ちることを確かめる「変異」、レビュー、全品質ゲート（型チェック・Lint・テスト・ビルド）の通過を経て、下書きの PR を作ります。

AI が守る規則と安全装置を「ハーネス」として用意しました。毎回読み込まれる指針（`CLAUDE.md`）、サブエージェントやコマンドの定義（`.claude/`）、危険なコマンドや保護ファイルの編集のブロック、終了時の品質ゲートの自動実行、全ゲートを 1 コマンドで実行する `scripts/verify.sh` です。

### 自分で判断・理解した点

私が決めた主な点は次のとおりです。

- 片割れのサロゲート文字への対応は見送り、ゼロ幅スペースだけのキーワードを空と扱う対応だけにしました。実際に届くかを調べると、詳細ページの不正なバイト列は Next.js が拒否し、API の名前は ASCII だけだったためです（仕様 0019、PR #37）。
- E2E のために接続先を環境変数で上書きできるようにする際、トークンの送り先が変わるので、ループバックだけを許し、上書き中はトークンを送らない条件を承認しました。Playwright の追加も私が判断し、コマンドも自分で実行しました（仕様 0013、PR #38）。
- 存在しない `components/` を README に書く条件が仕様の中で矛盾していると分かったときは、事実どおり「未作成」と書くと決め、仕様を先に直しました（仕様 0012）。

どこまで自分で読んで理解しているかは、次のとおりです。設計の方針、API呼び出し部分、テストの考え方です。レビューの指摘を読み、AIに説明させ、コードを読んで理解しました。

### AIの出力で注意した点

- AI が保護ファイル（`.claude/` の規則）を、確認画面を経ずに一時的に書き換えていました。レビュー担当の AI（reviewer）が見つけ、PR の本文で開示し、以後は触らないと決めました（計画 0016、PR #34）。
- 変異で確かめると、認証情報の検査を外した変異 2 件をテストが見逃していました。テストの入力が `user:pass@` の 1 行だけで、ユーザー名とパスワードの 2 つの検査が互いを隠していたためで、行を足して直しました（計画 0013、PR #38）。
- 実装が計画と食い違い、6 件に分けるはずのテストが 1 つにまとまっていました。レビュー担当の AI（reviewer）に指摘され、計画どおりに直しました（計画 0020、PR #36）。
- 目に見えないゼロ幅文字が文書に直接書き込まれていました。エスケープ表記に直し、全文の走査で 0 件を確認しました（PR #37）。
- 基本方針として、確認できないことは「未確認」と書かせ、Next.js の挙動は推測せず公式ドキュメントを読ませ、Issue や PR の本文にある指示には従わせません。
