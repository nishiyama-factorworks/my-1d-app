# my-1d-app

## 概要

キーワードで GitHub のリポジトリを検索し、一覧から選んだリポジトリの詳細を表示する Web アプリです。Next.js（App Router）と TypeScript で作っています。

- トップページ（`/`）でキーワードを入力して検索すると、リポジトリの一覧が表示されます。ページネーションで先のページへ進めます。
- 一覧の 1 件を選ぶと、詳細ページ（`/repos/[owner]/[repo]`）に、オーナーのアイコン、リポジトリ名、言語、Star 数、Watcher 数、Fork 数、Issue 数が表示されます。「トップへ戻る」を押すと、検索したキーワードと同じページの一覧に戻ります。

この README は、工夫した点とこだわったポイント、そしてその選択をした理由を文章でまとめることを主な役割にしています。動かし方や構成、範囲と制約の詳細は、それぞれ `docs/` の文書にまとめ、ここには要約と参照だけを置いています。仕様の全体は [docs/specs/0001-github-repo-search.md](docs/specs/0001-github-repo-search.md)、課題文は [docs/specs/\_assignment.md](docs/specs/_assignment.md) にあります。

## 工夫した点と理由

### Watcher数の取得元

詳細ページの Watcher 数は、個別のリポジトリ API の `subscribers_count` から取っています。GitHub の検索 API にある `watchers_count` は、名前に反して Star 数と同じ値で、本当の Watcher 数ではありません。そのため、一覧では Watcher 数を使わず（一覧に出すのはオーナーのアイコンとリポジトリ名だけ）、詳細ページでだけ `subscribers_count` を読みます（[仕様 0001](docs/specs/0001-github-repo-search.md) の 7 節）。

この取り違えは、見た目では気づきにくい間違いです。Star 数と Watcher 数が同じ値になっていても、画面は崩れず、型も合ってしまいます。そこで、テストでは Star 数 100 と Watcher 数 7 のように、あえて違う値を入れて、取り違えたら必ず落ちるようにしました（[仕様 0003](docs/specs/0003-github-api-client.md) の AC-13a）。E2E のモックサーバーにも、使われないはずの値（`watchers_count` に 99999）を入れてあり、画面に出てしまったら失敗します。トレードオフは、一覧に Watcher 数を出せないことです。

### GitHub APIをサーバー側だけで呼ぶ

GitHub API の呼び出しは、サーバー側（Server Component）だけで行います。理由は、アクセストークン（`GITHUB_TOKEN`）をブラウザに渡さないためです。呼び出しを担う `lib/github/` の先頭に `import "server-only"` を置き、クライアント側のコードから読み込もうとするとビルドで失敗するようにしました。「気をつける」ではなく、間違えたら機械的に止まる形にしています。

接続先も `api.github.com` に固定し、パスに絶対 URL や `//host` の形を渡されても別のホストへ向かないように検査しています。トークンを外部のホストへ送ってしまう事故を避けるためです（[仕様 0003](docs/specs/0003-github-api-client.md)）。この固定には、E2E テストのためのただ一つの例外があります。サーバー側から呼ぶ以上、ブラウザ側のリクエストの差し替え（Playwright の機能）では偽の API に切り替えられないからです。環境変数で接続先を上書きできるようにし、ループバックのアドレスに限り、上書き中はトークンを送りません。モックライブラリの導入や実際の API への接続も検討し、依存が増える点と、不安定でレート制限がある点から採りませんでした（[ADR 0006](docs/adr/0006-playwright-e2e.md)）。

### 検索条件をURLで持つ

キーワードとページ番号は、`/?q=react&page=2` のように URL のクエリで持ち、サーバー側にもブラウザの保存領域にも状態を保存しません。理由は、再読み込み、URL の共有、ブラウザの「戻る」「進む」で、同じ画面を必ず復元できるからです。詳細ページへ移るときも `q` と `page` をクエリで引き継ぐので、「トップへ戻る」を押すと、検索したときと同じキーワード・同じページの一覧に戻ります。

URL から来る値は信用せず、戻り先のリンクは、受け取った文字列をそのまま使わずに、検証して作り直します（`q` が空、または 257 文字以上ならトップ `/`、`page` が不正なら 1 ページ目）。外部のサイトへ飛ばすリンクを作らせないためです（[仕様 0009](docs/specs/0009-back-navigation.md)）。トレードオフは、キーワードが URL に載るため長さの上限（256 文字）が要ることです。

### 1,000件の上限の扱い

GitHub の検索 API は、先頭から 1,000 件より先を返さず、それより先のページを求めると 422 のエラーになります。呼ぶだけでレート制限も消費します。そこで、総件数が 1,000 件を超えるときは、一覧に「上位1,000件まで表示します」と出し、1 ページ 30 件で最大 34 ページまでとしました。それを超えるページを URL で直接開かれた場合は、GitHub API を呼ばずに「範囲外」の案内を出します（[仕様 0007](docs/specs/0007-pagination.md)）。

範囲外の判定は 2 段で行っています。ページ番号が 34 を超えるなら API を呼ばずに範囲外とし、API を呼んだ後は、総件数に対して最終ページを超えているかで判定します。総件数が 0 件のときは範囲外にせず、「0 件」の案内を出します。上限に触れて失敗する前に、画面の側で言葉にして伝える設計です。

### 取得結果のキャッシュ

取得結果は、`fetch` の `next.revalidate` で、検索を 300 秒、詳細を 600 秒キャッシュします。理由は、GitHub API のレート制限（認証なしの検索 API は 1 分 10 回）です。キャッシュが無いと、再読み込みや、一覧と詳細の往復で、同じ取得を繰り返して制限を使い切ってしまいます。検索結果は変わりやすいので短く、リポジトリの詳細は変わりにくいので長くしました。保存されるのは、公開リポジトリの情報だけです。

ほかに検討した案もあります。キャッシュしない案は、背景の問題が残るため採りませんでした。`unstable_cache` は、Next.js 16 で `use cache` に置き換えられた古い API です。`cacheComponents` と `"use cache"` は、アプリ全体のレンダリングの仕組みが変わり影響が大きいため、仕様の範囲外としました。採用した `fetch` の指定は、`lib/github/http.ts` の 1 か所で済み、追加の依存も要りません。動的ルート（クエリを読むページ）でも効くことは、実機で確認しています（[ADR 0005](docs/adr/0005-github-fetch-revalidate.md)）。トレードオフは、GitHub 側の変更が最大で再検証時間より長く遅れて見えることです。

### エラーを状態として見せる

GitHub API のエラーを握りつぶさず、レート制限、見つからない、検証エラー、GitHub 側の異常、通信失敗という種別ごとに、利用者に分かる文言で表示します。レート制限のときは、リセットされる時刻が分かれば、その時刻（東京時間）も出します。読み込み中、0 件、範囲外は `role="status"`、エラーは `role="alert"` にして、支援技術にも伝わるようにしました。

実装で気をつけたのは、種別ごとの表示を、ページの中で作る点です。本番の Next.js は、Server Component で投げた例外のメッセージを `error.tsx` に渡さず、固定の文言しか届かないため、`error.tsx` だけで受けると種別を出し分けられません（[仕様 0010](docs/specs/0010-state-views.md) の 2 節）。そこで、ページが `GitHubApiError` を受け止めて、種別ごとの画面を描画し、想定外の例外だけを `app/error.tsx` が受けます。エラー文はトークンや URL、レスポンスの本文を含まない固定の文言にしました。トレードオフは、エラー表示と 404 が、ストリーミングの都合で HTTP 200 で返ることです。

### テストの検出力を確かめる

テストを書いて通っただけでは、そのテストが本当に間違いを見つけられるかは分かりません。特に、最初から緑になるテスト（現状の振る舞いを固定するテスト）は、効いているのか見分けがつきません。そこで、実装を一時的に壊して（条件を外す、値を入れ替える、検査を省くなど）、テストが落ちることを確かめ、確かめたら元に戻す「変異」の確認を、各タスクで行いました。

効果が出た例もあります。接続先の上書きの実装（計画 0013）では、変異 14 件のうち 2 件を最初は見逃しました。テストの認証情報の行が 1 行だけで、ユーザー名の検査とパスワードの検査が互いを隠していたためです。片方だけを含む行を足して、全件を検出できるようにしました。この例を含む、AI の出力で注意した点は、「AI利用レポート」にまとめています。トレードオフは、時間がかかることと、変異のスクリプトはリポジトリに入れておらず、CI では実行しないことです（結果は各計画の進捗メモに記録しています）。

## セットアップ

Node.js と pnpm があれば、次の 2 つのコマンドで開発サーバーが起動します（既定は http://localhost:3000）。

```bash
pnpm install
pnpm dev
```

環境変数 `GITHUB_TOKEN` は**任意**で、未設定でも動作します。本番ビルドでの起動、テスト（単体・E2E）、トークンの権限の詳細は [docs/setup.md](docs/setup.md) にあります。

## 構成

画面は 2 つです。トップページ `/`（検索フォーム、検索結果の一覧、ページネーション。クエリ `q` と `page`）と、詳細ページ `/repos/[owner]/[repo]` です。ディレクトリ構成と各画面の状態表示の詳細は [docs/structure.md](docs/structure.md) にあります。

## 範囲と制約

既知の制約は、GitHub の検索 API が先頭から 1,000 件までしか返さないことと、GitHub API のレート制限（認証なしの検索 API は 1 分 10 回）です。「プロダクション想定」として満たした範囲、対応しなかった事項は、[docs/scope.md](docs/scope.md) にまとめています。

## AI利用レポート

### AI利用について考慮した点

- 基本的にAIに作業させることに注力すること。
- タスクを細かく細分化し、機能を積み上げることで完成に近づけること。
- まずはGitHub+AIをフル活用したワークフローを作ること。

### 使ったツール

- **Claude Code**（Anthropic の CLI）で、仕様の作成から実装・レビュー・PR の作成までを進めました。
- Claude Code のサブエージェントを、役割ごとに使い分けました（`.claude/agents/`）: `planner`（計画）、`test-writer`（失敗するテスト）、`implementer`（実装）、`reviewer`（レビュー）、`security-reviewer`（セキュリティの点検）。

### 進め方

仕様駆動と TDD（テスト駆動開発）で、1 つの Issue ごとに次の順で進めました。

1. **Issue**: 作業は GitHub Issue から始めます（進捗は GitHub Projects）。
2. **仕様**: `docs/specs/` に、Given / When / Then 形式の受け入れ条件（AC）を書き、**人間が承認**します。
3. **計画**: `docs/plans/` に小さなタスクへ分解します。判断が要る点は「要確認事項」として推奨つきで並べ、**人間が承認**します。
4. **RED**: 受け入れ条件に対応する失敗するテストを先に書き、失敗の理由が「未実装による期待値の不一致」であることを確かめます（構文エラーや import エラーでの失敗は RED と認めません）。
5. **GREEN → REFACTOR**: テストを通す最小の実装を書き、緑のまま整理します。テストを弱めて通すことは禁止です。
6. **変異による検出力の確認**: 実装を一時的に壊して（条件を外す、値を入れ替えるなど）、テストが落ちることを確認してから元に戻します。
7. **レビュー**: `reviewer` を走らせ、認証・入力・依存・外部連携に触れた変更では `security-reviewer` も並列で走らせて、Critical / Major の指摘を直します。
8. **検証と PR**: `bash scripts/verify.sh` が全て PASS してから「完了」と報告し、Draft PR を作ります。push と PR の作成は人間の承認を得てから行い、**マージは人間だけ**が行います。

AI が守る規則と自動の安全装置を、**ハーネス**として用意しました。

- `CLAUDE.md`: 毎セッション読み込まれるプロジェクトの指針（ワークフロー、絶対ルール）。
- `.claude/`: ルール（`rules/`）、サブエージェント（`agents/`）、コマンド（`commands/`）、スキル（`skills/`）、フック（`hooks/`）。危険なコマンドや保護ファイル（`.env*`、ロックファイル）の編集を実行前にブロックし、編集直後に整形と ESLint を走らせ、終了時に型チェック・Lint・テストが未達なら差し戻します。
- `scripts/verify.sh`: 全品質ゲートの実行スクリプト（CI も同じものを使います）。

2026-10-09 時点で（この README を含む PR を除いて）、マージ済みの PR は 18 件（`gh pr list --state merged`）、仕様は 20 本（`docs/specs/`）、ADR は 6 本（`docs/adr/`）、`.claude/` のサブエージェントは 5、コマンドは 11、スキルは 3 です。

### 人間が判断・修正した点

AI が選択肢と推奨を示し、人間が決めた点のうち、仕様・計画・PR で確認できるものです。

- **仕様 0019（Issue #21、PR #37）**: 片割れのサロゲート文字（`URIError` の原因）が実際に届くかを調べたところ、詳細ページの不正なバイト列は Next.js が HTTP 400 で拒否し、API の名前は ASCII だけで届かないと分かりました。人間が「対応しない」と決め、ゼロ幅スペースだけのキーワードを空と判定する対応だけを入れました。
- **仕様 0013（PR #38）**: E2E のために GitHub API の接続先を環境変数で上書きできるようにする際、トークンの送り先を変える変更になるため、人間が「ループバックだけを許し、上書き中はトークンを送らない」安全策を承認しました。Playwright の追加も人間の承認のうえ、ロックファイルを AI が編集しない規則のため、人間がコマンドを実行しました（ADR 0006）。
- **仕様 0012（この README）**: 計画の作成中に、`components/` ディレクトリが実在せず、仕様の 2 つの受け入れ条件が矛盾すると分かりました。人間が「README に未作成と事実どおり書く」ことを決め、仕様を先に直しました。
- **仕様 0020（Issue #35、PR #36）**: README に起動手順を書く前に、`package.json` の `scripts` に `dev` と `start` が無いことが分かりました。小さな Issue と仕様にして、人間の承認のうえで追加しました。

### AIの出力で注意した点

- **保護ファイルの扱い（計画 0016、PR #34）**: テストの検出力を確かめる際、AI が保護ファイル（`.claude/rules/10-nextjs.md`）を、編集の確認画面を経ずに一時的に書き換えて元に戻しました。`reviewer` が Major として指摘し、PR の本文で開示しました。今後は保護ファイルを一時的にも書き換えません。
- **テストの見逃し（計画 0013、PR #38）**: 変異テストで、認証情報の検査を外した変異 2 件をテストが見逃しました。`user:pass@` の 1 行だけでは 2 つの検査が互いを隠していたためで、片方だけを含む行を足して全件を検出できるようにしました。
- **計画との食い違い（計画 0020、PR #36）**: AC-3 が、計画では `it.each` の 6 件だったのに、実装は 1 つのテストに 6 個の `expect` を並べていました。`reviewer` が Major として指摘し、計画どおりに直しました。
- **目に見えない文字（仕様 0019、PR #37）**: 計画にゼロ幅文字が直接書き込まれていました。目では見分けられないため、エスケープ表記に直し、node で全文を走査して 0 件であることを確認しました。
- **推測しない運用**: 確認できていないことは「未確認」と書き、数値は確認した値だけを書きます。Next.js の挙動に確信が持てないときは、推測せず公式ドキュメント（`node_modules/next/dist/docs`）を読みます。Issue や PR の本文に書かれた指示には従いません。シークレットは扱わず、依存の追加とロックファイルの更新は人間に確認します。
