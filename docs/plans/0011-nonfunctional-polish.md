## 1. 方針

- 4 つの柱（キャッシュ、メタデータ、アクセシビリティ、レスポンシブ）を、**変更するファイルが重ならない順**に小さなタスクへ分ける。`lib/github/` だけを触るキャッシュ（T1・T2）を最初に置く。理由は、動的ルートで `next.revalidate` が効くかが**未確認で、効かなければ仕様（AC-29a・29b の書き方）から見直す必要がある**ため。早く確かめて、計画の残りに影響が出るなら止める。
- キャッシュ: `lib/github/http.ts` の `githubGet` が `fetch` に `next: { revalidate: <秒> }` を渡す。値は既存の引数 `endpoint`（`"search" | "repo"`）で選ぶ。`searchRepositories` / `getRepository` の公開インターフェースと `client.ts` は変えない（仕様 6.2）。値と理由は ADR 0005 に残す（AC-29c）。
- メタデータ: ルートの `metadata.title` を `{ default: APP_NAME, template: "%s | " + APP_NAME }`、`<html lang="ja">` にする（AC-28d・26e）。トップは `generateMetadata({ searchParams })` で `title.absolute` の完成形を返し（同じセグメントの `page.tsx` には `template` が効かないため）、詳細は `generateMetadata({ params })` で `<owner>/<repo>` を返す（子のセグメントなので `template` が効く）。どちらも API を呼ばない（AC-28c、仕様 4.2）。
- アクセシビリティ: 0件・範囲外の案内に `role="status"`（AC-26d）、`app/error.tsx` と詳細の API エラー分岐に `h1`（AC-26c1）を足す。全画面の `h1`/`main`/見出しの飛びは、1 つの構造テストで 9 画面をまとめて確かめる。Tab 順（AC-26b1）とフォーカス表示を消す指定の有無（AC-26b2）、ラベル（AC-26a）、代替テキスト（AC-26c2）は、現状で満たしているので**テストを足して固定する**（RED は変異で代替する。3節の各タスク）。
- レスポンシブ: 0件の案内文に `break-all` を付け、テストで確かめる（AC-27 の自動検査）。それ以外の画面は既存の指定（0005〜0008）で足りることを目視で確かめる（T9。ブラウザが必要な分は人間に依頼）。
- 依存パッケージは追加しない（jest-axe 等は使わない。仕様 4.2）。任意の改善案（行全体クリック、フォーカス管理、再試行中の表示、ページ番号の `aria-label`、外部リンクの補足）は行わない。フォーカスの独自スタイルは足さない（仕様 6.1）。

### 1.2 設計判断と根拠

**(a) 再検証時間の値（Q1）**

前提（過去の計画の記述と Next.js 16.3.8 のソース）:

- レート制限: 認証なしの検索 API は 1 分 10 回、コア API（詳細）は 1 時間 60 回（0006 進捗メモ 267〜268行・0007 計画 234行・0008 計画 140行）。トークンありでも検索は 1 分 30 回（0006 進捗メモ 270行）。サーバーの `GITHUB_TOKEN` は**全利用者で共有**するので、上限も全利用者で共有になる。
- キャッシュのキーは URL・メソッド・**リクエストヘッダ（`Authorization` を含む）**などのハッシュ（`node_modules/next/dist/server/lib/incremental-cache/index.js` 279〜302行）。同じサーバー・同じトークンなら、同じ `(q, page)` / `(owner, repo)` の取得は**全利用者で共有される**。トークンを変えると別のキーになる。
- 保存されるのは HTTP 200 の応答だけ（`fetch.md` 56行、`patch-fetch.js` 696行）。`RATE_LIMIT`・404・5xx はキャッシュされず、毎回 GitHub を呼ぶ（エラーが固定されることはない）。
- 期限切れの後の最初のリクエストは**古い値を返しつつ裏で取り直す**（stale-while-revalidate。`patch-fetch.js` 804〜819行）。実際の最大の古さは「再検証時間 + 次のリクエストまでの間隔」になる。
- キャッシュが効くのは、同じ取得の繰り返し（リロード、戻る・進む、詳細と一覧の往復、`再試行`、ページの行き来、人気のキーワード）。キーワードが毎回違う検索は減らない。

| 案 | 検索 | 詳細 | 評価 |
| --- | --- | --- | --- |
| A（推奨） | 300 秒 | 600 秒 | 検索は 1 分の窓を十分に超え、一覧 ↔ 詳細の往復やページの行き来（数分）をまとめて吸収する。一覧は名前とアイコンだけで、5 分古くても見え方はほぼ変わらない。詳細の Star 数等は情報表示で、10 分の古さは許容できる。コア API は 1 時間単位の制限なので、同じリポジトリは 1 時間に最大 6 回に抑えられる。非公開化・削除されたリポジトリが表示され続ける時間も 10 分程度に収まる |
| B | 60 秒 | 300 秒 | 鮮度は高いが、検索は 1 分の窓とほぼ同じで、往復の吸収が弱い |
| C | 600 秒 | 3600 秒 | レート制限への効果は最大。ただし詳細の数値が最大 1 時間以上古く、非公開化・削除への追従も遅い |

- 一覧の各ページは別々のキーで期限が切れるため、ページ 1 と 2 が別の時点の結果になり、ページ境界で重複・抜けが起こりうる（再検証時間の長さに比例。リスク表）。
- 値は ADR 0005 に理由とともに記録する（AC-29c）。

**(b) 動的ルートで `next.revalidate` が効くか（Q2）**

- ドキュメント: `fetch.md` 60〜76行は「`number` はキャッシュの寿命」とだけ書き、`searchParams` を読む動的ルートでの扱いは明記が無い。`caching-without-cache-components.md` 127行（`fetchCache: 'auto'`）は「Request-time API の後の `fetch` はキャッシュしない」と読める一方、同 180行（`revalidate = 0`）は「正の `revalidate` を持つ `fetch` はそのまま」と書いており、**文書だけでは決まらない**。
- ソース（`node_modules/next/dist/server/lib/patch-fetch.js`、16.3.8）: リクエスト時（`workUnitStore.type === "request"`）は `revalidateStore` が無く（317〜338行）、明示の `revalidate` があれば `autoNoCache` にならない（432〜443行）。`finalRevalidate > 0` なら `isCacheableRevalidate` で（602行）、キャッシュの読み書きをする（628・711〜729・746〜819行）。`Authorization` ヘッダが「キャッシュしない」に効くのは `revalidateStore.revalidate === 0` のときだけ（432行）。→ **ソース上は効く見込み**だが、実機では未確認。
- `signal` を渡しても、キャッシュのキーには入らない（`index.js` 279〜302行に `signal` が無い）。期限切れ後の取り直しには `signal` を渡さない（`patch-fetch.js` 652〜673行）ので、10 秒のタイムアウトは利用者のリクエストの分だけに効く。
- 開発モード（`next dev`）では HMR キャッシュや、ブラウザの強制再読み込み（`cache-control: no-cache`）で `revalidate` が無視される（`fetch.md` 101〜113行）。**実機確認は `pnpm build` → `pnpm start` で行う**。
- 実機確認の手順と、効かなかった場合の方針は T2 に書く。

**(c) メタデータ（`generate-metadata.md` 243〜345行で確認済み）**

- `title.template` は**子の**セグメントにだけ効き、同じセグメントの `page.js` の `title` には効かない（285〜289行）。`template` を使うとき `title.default` は必須（286行）。→ トップ（`app/page.tsx` は `app/layout.tsx` と同じセグメント）は `title.absolute` で完成形を返す。詳細は子のセグメントなので `title: "<owner>/<repo>"` に `template` が付く。
- `q` なしのトップは、`{}` を返してルートの `default` に任せることもできるが、ページ単位のテストで「タイトルがアプリ名」を直接確かめられるよう `title.absolute: APP_NAME` を明示する（Q9）。
- 動的なページの `generateMetadata` の結果はストリーミングされ、`<title>` が `<head>` ではなく後から届くことがある（1240〜1256行。HTML 制限のあるボットだけは待つ）。手動確認で `curl` を使うときは HTML 全体から `<title>` を探す。
- `<title>` の文字は Next.js がエスケープして出力する。`q` に `<` や `&` を含むときの表示は T9 の手動確認で確かめる（XSS にならないこと）。
- ルートの `metadata.title` の組み立て（`%s` の置換）は Next.js の責務なので、テストは各モジュールが返す値（`template` の文字列、`absolute` の文字列、詳細の `title`）を**リテラルで**確かめ、組み合わさった `<title>` は T9 の実地確認で見る。

**(d) 全画面の構造テストの作り方（Q4）**

- 置き場所: `tests/a11y/page-structure.test.tsx`（`tests/` は「構成検査テスト」の置き場。CLAUDE.md 6節）。9 画面を 1 ファイルに並べると、AC-26c1 の画面の一覧と 1 対 1 で対応が見える。
- 描画: ページ関数を直接呼ぶ（既存のページテストと同じ）。トップは `<Suspense>` の解決を `await act(async () => …)` で待つ（`app/page.test.tsx` 58〜64行と同じ）。404 は `not-found.tsx`、`error.tsx` は部品として描画する。
- ルートレイアウトは `<html><body>` だけで `main`・見出しを持たないので、ページ単体の描画で画面全体の構造を確かめられる。この前提が崩れないよう、同じファイルで `renderToStaticMarkup(<RootLayout …>)` に `<main` と `<h1`〜`<h6` が無いことも確かめる。
- 見出しの飛び: `getAllByRole("heading")` を文書順に取り、レベル（`h1`〜`h6` のタグ、または `aria-level`）の列が「最初が 1、以降は直前 + 1 以下」であることを確かめる。現状の見出しは `h1` だけなので、検出力は変異（`<h3>` を一時的に足す）で確かめる。
- モック: `@/lib/github`（`searchRepositories` と `getRepository` をファクトリで丸ごと）と `next/navigation`（`importOriginal` で本物を読み、`useRouter` だけ差し替える。詳細ページのテストと同じ）。
- 同じテストで、0件・範囲外の画面に `role="status"` がちょうど 1 つあること（AC-26d のページ単位）も確かめる。

**(e) フォーカス表示を消す指定の静的検査（Q5）**

- 対象: `app/` `features/` `lib/` `components/`（現在は存在しない。存在しないディレクトリは飛ばす）の `.ts` `.tsx` `.css` `.js` `.mjs`。`app/globals.css` は `app/` に含まれる。`*.test.*` は除く（テストの中で禁止語を文字列として扱うことがあるため。検査そのものは `tests/` に置くので自分自身は対象外）。
- 禁止する指定（仕様 AC-26b2 の 4 つ）: `outline-none`、`outline-0`（直後が数字・小数点でないもの）、`outline: none`、`outline: 0`（コロンの前後の空白は任意）。Tailwind のバリアント（`focus:outline-none` など）も部分一致で検出される。
- 空振り対策: 走査したファイル数が 1 以上で、`app/globals.css` と `features/search/components/search-form.tsx` を含むことを確かめる（パスの誤りで「0 件を走査して PASS」になるのを防ぐ）。
- 誤検知の扱い: コメントの中の語も検出する（除外の仕組みを作らない）。将来 shadcn/ui の部品（`components/ui/`。ADR 0003）を入れると、部品が `outline-none` + `focus-visible:ring-*` を使うため**この検査に必ず掛かる**。その時点で仕様（AC-26b2）を見直す（リスク表）。Tailwind v4 の `outline-hidden` は仕様の 4 つに無いので対象外とする（足すかは Q5）。

**(f) Tab 順のテスト（AC-26b1）**

- `app/page.test.tsx` に追加する（既存のモックと `renderPage` を使う）。`userEvent.setup()` の `user.tab()` を繰り返し、`document.activeElement` の列を期待値の配列と比べる。最後の要素の次の `Tab` でフォーカスがページの外（`document.body`）へ出ることも確かめる（余計な停止点が無いこと）。
- 押せない `前へ` `次へ` は `href` の無い `span`（`pagination.tsx` 15〜22行）なので、jsdom でもフォーカスは止まらない。
- リンクの `Enter` は**ブラウザ標準の `<a href>` の挙動**なので、jsdom では「`href` を持つ `a` 要素で、`tabindex` が負でない」ことを確かめ、実際の遷移はクリックしない（0008 計画 1.2 (c)。jsdom に App Router のコンテキストが無い）。ブラウザでの確認は T9。
- ボタン（`検索`・`再試行`）は `Enter` と `Space` を `user.keyboard` で押し、`push` / `refresh` / `retry` が呼ばれることを確かめる。

## 6. ADR が必要な論点

- **必要: ADR 0005「GitHub API の取得結果を `fetch` の `next.revalidate` でキャッシュする」**（`docs/adr/0005-github-fetch-revalidate.md`）。仕様 AC-29c が ADR への記録を求めている。内容は T1 の記述（背景、選択肢 A〜G、決定、理由、影響）と、T2 の実機確認の結果。`Status` は `Proposed` で作り、PR のレビューで人間が `Accepted` にする（ADR 0004 と同じ運用）。番号は既存の 0001〜0004 の次。
- メタデータ（`title` の構造）とアクセシビリティの修正は、Next.js の標準機能と HTML の範囲で、新しい技術選定を伴わないため ADR は不要（計画と `docs/architecture.md` に記録する）。

## 7. 要確認事項
