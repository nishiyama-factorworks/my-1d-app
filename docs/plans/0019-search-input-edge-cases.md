## 1. 方針

- 変更するのは `lib/search/query.ts` の `normalizeKeyword` だけ。シグネチャ `(input: string) => string | null` は変えない（仕様 6 節）。`parseSearchParams` は内部で `normalizeKeyword` を呼んでいる（`query.ts` 31 行目）ので、AC-4 は `parseSearchParams` を変えずに満たされる。
- 実装の形（想定）:
  1. 入力からゼロ幅文字（U+200B・U+200C・U+200D・U+2060 の 4 つ）を除いた文字列を作り、それを `trim()` した結果が空なら `null` を返す。
  2. そうでなければ、**元の入力**を `trim()` した値を返す（ゼロ幅文字は取り除かない。仕様 4.2・AC-3）。
  - 「除いてから trim」の順にする理由: `trim()` を先にしてから除くと、`ZW・半角空白・ZW` のように空白がゼロ幅文字に挟まれた入力で空白が残り、空と判定できない（仕様 4.1 の「空白とゼロ幅文字だけの入力は空」に反する）。この形は AC-2 の追加ケースで固定する（Q2）。
- ゼロ幅文字の指定は、ソース上で `\u200B` のような**エスケープで書く**（文字クラス `[\u200B\u200C\u200D\u2060]` の正規表現など。書き方は実装時に決めてよい）。ゼロ幅文字そのものをソース・テストに直書きしない。理由: 目に見えず、レビューで判別できない・エディタや整形で消える／混入する危険があるため（ESLint の `no-irregular-whitespace` の対象にもなりうる）。
- 範囲は 4 文字に固定する。`\p{Cf}` などの広いクラスは使わない（仕様 4.2「ゼロ幅文字以外の不可視文字は扱わない」。U+FEFF は `trim()` が既に除く）。
- `query.ts` の既存コメント（「trim は全角空白…」）に、ゼロ幅文字を別扱いする理由（ECMAScript の `trim()` の対象外であること、仕様 0019）を 1 行添える。
- 既存テスト（AC-25a・AC-25b など）は期待値を変えない（AC-5）。依存パッケージの追加は無い。

## 5. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 範囲を広げすぎる（`\p{Cf}`・`\s` など） | 仕様外の文字（U+202E など）まで空判定に影響し、仕様 4.2 に反する | 4 文字を明示した文字クラスに限る。レビューで確認（検出力確認 5 の限界） |
| 空でない入力を書き換えてしまう（ゼロ幅文字を除いた値を返す） | 検索語が利用者の入力と変わる（仕様 4.2 違反） | AC-3 で固定。検出力確認 3 |
| ゼロ幅文字の直書き | レビューで見えない、整形で消える・混入する | エスケープで書く。T1 の完了条件で Grep による 0 件を確認 |
| 既存の振る舞いの退行（全角空白・タブ・改行の空判定、前後の空白除去） | 空入力の判定や検索語が変わる | AC-5 として既存テストを無変更で通す。検出力確認 6 |
| 呼び出し元の挙動変化 | フォーム・トップ・戻り先の表示が変わる | いずれも既存の `null` 分岐に合流するだけ（1.1）。既存テストを無変更で通す |
