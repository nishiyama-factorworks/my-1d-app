# 0004: Ready にできるタスクを、仕様の依存からスクリプトで機械的に抽出する

- Status: Proposed
- 日付: 2026-10-08
- 決定者: 人間（プロジェクト担当者）。Issue #25 の `/feature` 中に方針（スクリプト + 完了報告、更新は `--apply` のときだけ）を回答。ADR の承認は PR のレビューで行う

## 背景

MANUAL 10.4 では「Ready は人間が動かす」「Claude はボードの状態を自動では変更しない」としていた。一方で各仕様の「関連:」行には「依存: NNNN」があり、前提のタスクが完了したかどうかは機械的に判定できる。人間が手作業で照合すると手間がかかり、漏れる。Issue #25 では、前提が完了したタスクを Ready の候補として出し、人間が承認して Project の Status を更新できる仕組みを求められた。

制約:

- Project の読み書きには `project` スコープが必要で、認証情報は人間だけが扱う（`gh auth refresh` は Claude に禁止している）。
- 状態の管理元は引き続き GitHub Projects（ADR 0002）。
- 依存パッケージを追加しない（`CLAUDE.md` の絶対ルール）。

## 検討した選択肢

### 案A: 現状のまま（人間が手で照合して Ready に動かす）

- メリット: 変更が要らない。
- デメリット: 照合の手間と見落とし。タスクが増えるほど悪化する。

### 案B: スクリプトが候補を出し、人間が承認して `--apply` で更新する

- メリット: 依存の照合を機械化できる。書き込みは `--apply` のときだけで、Backlog から Ready への更新に限る。確認を二重に挟める。追加の依存が要らない（Node の標準機能と `gh` のみ）。
- デメリット: スクリプトと、ハーネスの規則の保守が増える。`gh project` の出力の形に依存する。

### 案C: GitHub Actions で自動更新する

- メリット: 人手が要らない。
- デメリット: Project の権限をもつトークンをシークレットに置く必要がある。シークレットは扱わないというハーネスの方針と衝突する。

### 案D: Projects 組み込みの Workflows を使う

- メリット: 設定だけで済む。
- デメリット: 仕様の「依存」を条件にできない。

## 決定

案B を採用する。`scripts/ready-issues.mjs` が、仕様の「依存」と Issue の状態から Ready にできる Issue を表示する。`--project <番号>` で Status を読み取って更新予定を表示し、`--apply` を付けたときだけ Backlog から Ready へ更新する。`/feature` の完了報告には、読み取りだけの結果（この PR がマージされたら着手できるタスク）を載せる。

## 理由

- 判定の入力（仕様の依存、Issue の状態）がリポジトリと GitHub にあり、機械的に決まる。
- 書き込みを `--apply` に限り、`settings.json` の ask と `guard-bash.sh` の確認（スクリプトが内部で `gh project item-edit` を呼ぶため、既存の `gh` の確認が効かない）で二重に守れる。評価の順序は deny → ask → allow だが、`settings.json` 側の挙動は実機で確認していない。確認が出ることは hook が保証する。
- 認証情報は扱わない。`project` スコープの付与は人間が自分のターミナルで行う。

確認できていない点（未確認）:

- 実際の `--apply` の動作と、`gh project field-list` / `item-list` の出力の形（`fields` / `items`、Status のキー名）。テストは想定した JSON で書いている。`project` スコープの付与後に、初回は `--apply` なしで更新予定を確認する。
- hook と `settings.json` の変更は、セッションの再起動で反映される。

## 影響・トレードオフ

- 良くなること: 依存の照合の手間と見落としが減る。完了報告で次に着手できるタスクが分かる。
- 悪くなること / 受け入れるリスク:
  - hook はサンドボックスではない（MANUAL 10.7）。`node -e` で `gh project item-edit` を直接呼ぶ、別名にコピーして実行する、といった迂回は hook では止められない。これらは `settings.json` の allow に無いため、既定の確認に落ちる。
  - `guard-bash.sh` の照合は、コミットメッセージに `ready-issues.mjs` と `--apply` を書いただけでも確認になる（安全側の誤検知として受け入れる）。
- 追従が必要な更新: MANUAL 4.5・10.1・10.2・10.4・10.5・10.9・10.10・付録 A、`.claude/commands/feature.md`、`.claude/settings.json`、`.claude/hooks/guard-bash.sh`。ADR 0002 は変更しない（状態の管理元は引き続き Projects）。
