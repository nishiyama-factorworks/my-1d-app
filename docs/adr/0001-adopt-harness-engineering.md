# 0001: Claude Code によるハーネスエンジニアリングを開発方式として採用する

- Status: Accepted
- 日付: <導入日>
- 決定者: <名前>

## 背景
AI エージェントに開発を任せる際、プロンプトでの依頼だけでは品質が人と運に依存し、再現性がない。エージェントが誤りを犯しても、自動で検知・修正される仕組み（ハーネス）が必要。

## 検討した選択肢
### 案A: 都度プロンプトで依頼する
- メリット: 導入コストがゼロ
- デメリット: ルールが毎回ぶれる。検証が人手に依存する

### 案B: CLAUDE.md だけを整備する
- メリット: 軽量
- デメリット: 指示は「助言」であり強制力がない。守られたかを機械的に確認できない

### 案C: ハーネス一式（指示 + 決定論的ガード + 自動検証 + 役割分担）を整備する
- メリット: ルール違反は hook でブロックされ、品質ゲートで自動検証される。工程が再現できる
- デメリット: 初期整備と保守のコストがかかる

## 決定
案C を採用する。構成は `docs/harness/MANUAL.md` に従う。

## 理由
指示（CLAUDE.md / rules）は確率的にしか守られないが、hooks・permissions・CI は決定論的に働く。重要な規約はこちらに寄せることで、AI 駆動開発の品質を人に依存させずに保てる。

## 影響・トレードオフ
- 良くなること: 品質の再現性、レビュー負荷の低減、失敗からの学習（ルール化）
- 受け入れるリスク: ハーネス自体の保守が必要。ガードが厳しすぎると作業が止まる（`harness.env` で強度を調整する）
- 追従が必要な更新: ハーネスを変更したら MANUAL と本 ADR の関連箇所を確認する
