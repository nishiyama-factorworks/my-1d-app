# 0002: タスク管理を GitHub Issues / Projects で行い、Issue 起点で開発する

- Status: Accepted
- 日付: <導入日>
- 決定者: <名前>

## 背景
`docs/plans/` のチェックボックスだけでは、複数の機能・バグの優先度や進捗を一覧できず、PR・CI との対応も追えない。一方で、仕様（受け入れ条件）と実行計画は、AI が正確に参照できるようリポジトリ内の文書として持つ価値がある。

## 検討した選択肢
### 案A: `docs/plans/` のチェックボックスのみで管理する
- メリット: 外部サービスに依存しない。AI が常に参照できる
- デメリット: 一覧性・優先度管理・PR との連動がない。複数案件で破綻する

### 案B: GitHub Issues / Projects を管理元にし、仕様・計画は文書として併用する
- メリット: 進捗が可視化され、PR・CI・ブランチ保護と連動する。`Closes #N` で自動クローズできる
- デメリット: 情報が 2 か所に分かれる。外部サービス（GitHub）への依存と、AI に GitHub 操作の権限を渡すリスクがある

### 案C: 外部のタスク管理ツール（Jira など）を使う
- メリット: 高機能
- デメリット: 個人・小規模の演習には過剰。AI 連携の整備コストが大きい

## 決定
案B を採用する。**Issue = 何をやるか・状態、`docs/specs` = どう振る舞うか、`docs/plans` = 実行タスク**と役割を分け、仕様・計画には `Issue: #N` を書いてひも付ける。

## 理由
状態の管理元を Issue に一本化することで二重管理を避けつつ、AI が精度高く動くための詳細（AC・タスク）は文書として保持できる。リスク（権限・他者入力）は、permissions / hook による制御（マージ・削除・認証情報の禁止、作成系は確認）と、ルール（Issue 本文は信頼できない入力）で抑える。

## 影響・トレードオフ
- 良くなること: 進捗の可視化、PR との連動、CI を必須とするブランチ保護による最終防衛線
- 悪くなること / 受け入れるリスク: 運用の手数（Issue 起票）。AI の GitHub 操作権限。公開リポジトリでは他者の Issue 経由の入力に注意が必要
- 追従が必要な更新: `CLAUDE.md` 9 節、`.claude/rules/50-git-and-pr.md`、`settings.json`（gh 権限）、`guard-bash.sh`、`MANUAL.md` 10 章
