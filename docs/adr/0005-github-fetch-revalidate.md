# 0005: GitHub API の取得に fetch の next.revalidate で再検証時間を設定する

- Status: Proposed
- 日付: 2026-10-08
- 決定者: 人間（プロジェクト担当者）。Issue #11 の `/feature` 中に再検証時間（検索 300 秒・詳細 600 秒）を決定。ADR の承認は PR のレビューで行う

## 背景

GitHub API にはレート制限がある。

- 認証なしの検索 API は 1 分 10 回、コア API（詳細）は 1 時間 60 回。認証ありでも検索は 1 分 30 回（`docs/plans/0006-search-results-list.md`・`0007`・`0008` の実測・記述）。
- サーバーの `GITHUB_TOKEN` は全利用者で共有するため、上限も全利用者で共有になる。
- キャッシュが無いと、リロード、戻る・進む、一覧と詳細の往復、`再試行` といった同じ取得の繰り返しでレート制限を使い切る（0006・0008・0010 のレビューからの申し送り）。

仕様 0011 の AC-29a・29b は、検索と詳細の取得に再検証時間を設定することを求めている。AC-29c は値と理由の記録を求めている。

## 検討した選択肢

### 案A: `fetch` の `next.revalidate`（採用）

- メリット: `lib/github/http.ts` の 1 か所で済み、`searchRepositories` / `getRepository` の公開インターフェースが変わらない。取得（URL・ヘッダ）ごとにキャッシュされる。エンドポイントごとに値を変えられる。追加の依存が要らない。
- デメリット: 動的ルート（`searchParams` を読むページ）で実際に効くかは、ドキュメントだけでは決まらない（実機確認の節を参照）。

### 案B: キャッシュしない

- メリット: 常に最新。実装が要らない。
- デメリット: 同じ取得の繰り返しでレート制限を使い切る。背景の問題が残る。

### 案C: `unstable_cache`

- メリット: 関数単位でキャッシュできる。
- デメリット: Next.js 16 で `use cache` に置き換え済みの API である。キーに `Authorization` が入らない点の検討が要る。

### 案D: `cacheComponents` / `"use cache"`

- メリット: Next.js 16 の推奨の方式。
- デメリット: 仕様の Non-goals である。全体のレンダリングモデルが変わり、影響が大きい。

### 案E: ルートセグメントの `revalidate` / `fetchCache`

- メリット: ファイルに 1 行足すだけで済む。
- デメリット: `searchParams` を読む動的ルートでは画面全体のキャッシュにならず、`fetch` 単位の指定と同じ判定に行き着く。検索と詳細で値を分ける目的にも合わない。

### 案F: 独自のメモリキャッシュ

- メリット: 挙動を自分で制御できる。
- デメリット: 複数インスタンスで共有されない。実装と保守が増える。

### 案G: IP 単位の制限

- メリット: 利用者ごとの使いすぎを抑えられる。
- デメリット: 仕様の Non-goals である。サーバー側のトークン共有の問題は、キャッシュなしでは解決しない。

## 決定

案A を採用する。`lib/github/http.ts` の `githubGet` が `fetch` に `next: { revalidate }` を渡し、値は検索 300 秒（5 分）、詳細 600 秒（10 分）とする。`cache` オプションは指定しない（`no-store` と併記すると両方無視される）。

## 理由

値の根拠（計画 `docs/plans/0011-nonfunctional-polish.md` 1.2 (a)）:

- 検索の 300 秒は、レート制限の 1 分の窓を十分に超え、一覧と詳細の往復やページの行き来（数分）をまとめて吸収する。一覧は名前とアイコンだけで、5 分古くても見え方はほぼ変わらない。
- 詳細の 600 秒は、コア API の 1 時間単位の制限に対し、同じリポジトリを 1 時間に最大 6 回に抑える。スター数などの情報表示は 10 分遅れても許容できる。非公開化・削除されたリポジトリが表示され続ける時間も 10 分程度に収まる。
- 鮮度を優先する案（60 秒・300 秒）は往復の吸収が弱く、レート制限を優先する案（600 秒・3600 秒）は詳細の数値と非公開化・削除への追従が遅すぎる。

キャッシュしてよい根拠:

- 非公開と確認できないリポジトリは 0003 で利用者に返さないので、**利用者に返す**のは公開データだけである。利用者ごとに変わる情報を含まない。ただし 0003 の公開判定はキャッシュの後に行われるため、**ディスクのキャッシュには GitHub の生の応答が入る**（`GITHUB_TOKEN` が非公開リポジトリを読める権限を持つと、その情報もディスクに残る。次の「受け入れるリスク」を参照）。
- キャッシュのキーはリクエストヘッダ（`Authorization` を含む）も含む。同じサーバー・同じトークンなら取得は全利用者で共有され、トークンを変えると別のキーになる。
- 200 以外の応答はキャッシュされない。公式ドキュメント `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/fetch.md` の記述: 「Only responses with a `200` HTTP status code are stored.」（56 行）。`RATE_LIMIT`・404・5xx は毎回 GitHub を呼び、エラーが固定されることはない。
- `signal`（10 秒のタイムアウト）はキャッシュのキーに入らず、そのまま渡す。

## 影響・トレードオフ

- 良くなること: 同じ取得の繰り返し（リロード、戻る・進む、一覧と詳細の往復、`再試行`、ページの行き来、人気のキーワード）でレート制限の消費が減る。キーワードが毎回違う検索は減らない。
- 悪くなること / 受け入れるリスク:
  - データが最大で再検証時間だけ古くなる。
  - 期限切れの後の最初のリクエストは古い値を返し、裏で取り直す（stale-while-revalidate）。実際の最大の古さは「再検証時間 + 次のリクエストまでの間隔」になる。
  - 一覧の各ページは別々のキーで期限が切れるため、ページ 1 と 2 が別の時点の結果になり、ページ境界で重複・抜けが起こりうる。
  - 非公開化・削除への追従が最大で再検証時間だけ遅れる。
  - GitHub の応答（本文と応答ヘッダ）がサーバーの `.next/cache/fetch-cache/` に保存される。保存されるのは GitHub の生の応答で、`GITHUB_TOKEN` が非公開リポジトリを読める権限を持つ場合は、その名前や説明もディスクに残る（利用者には返さない）。応答ヘッダには、認証ありのとき GitHub が返すトークンの権限範囲・期限に関するヘッダが含まれうる（実機では見ていない。トークンの値そのものは保存されず、キャッシュキーはトークンを含む文字列の SHA-256）。**運用上の対策: `GITHUB_TOKEN` は公開リポジトリだけを読める最小権限のもの（スコープなしのクラシック PAT、または fine-grained PAT の「Public repositories (read-only)」。0003 の方針）にする。**
  - **ディスク上のキャッシュに上限が無い。** 期限が切れたエントリを消す処理は Next.js 側に無く（メモリ側は 50MB の LRU）、同じキーで上書きされるまで残る。毎回違うキーワードや大きいページ番号で取得を繰り返すと、GitHub のレート制限（認証ありの検索は 1 分 30 回）の範囲でエントリが増え続ける（応答は 1 件あたり約 1.5KB〜数百 KB、上限 2MB）。キャッシュを入れる前は何も書いていなかったため、新しく増えるリスクである。自前のサーバー（`next start`）で長く運用する場合は、`.next/cache/fetch-cache/` の定期的な削除や容量の監視が必要。上限付きの `cacheHandler`（LRU や TTL のあるストア）への置き換えは、依存の追加と ADR が必要なため、この決定の範囲外とする。マネージドなホスティングでは事業者の上限と退避に任せる形になる（未確認）。
  - 動的ルート（`searchParams` を読むページ）で `next.revalidate` が実際に効くかは、2026-10-08 に実機で確認した（「実機確認」の節）。認証ありの状態での確認と、再検証時間を過ぎた後の挙動（古い値を返して裏で取り直す）の確認は、まだ行っていない。
- 追従が必要な更新: `docs/architecture.md`（計画 T9 で更新）。

## 実機確認

2026-10-08、Next.js 16.3.8、`pnpm build` → `GITHUB_TOKEN= NEXT_PRIVATE_DEBUG_CACHE=1 next start -p 3111`（`GITHUB_TOKEN` を空にして起動。`.env*` は読まず、トークンの値も表示していない）。

- ビルド出力: `/` と `/repos/[owner]/[repo]` はどちらも動的（`ƒ`）。
- 検索（`/?q=cachecheck0011b`）を同じ URL で 3 回: キャッシュのログは「取得（ミス）→ 保存 → 取得（ヒット）→ 取得（ヒット）」。GitHub を呼んだのは 1 回だけで、2 回目以降はキャッシュから返った。
- 詳細（`/repos/vercel/swr`）を同じ URL で 3 回: 検索と同じ「ミス → 保存 → ヒット → ヒット」。コア API の残り回数（認証なしの枠）は 52 から 51 に 1 だけ減った（3 回取得して 1 回分）。
- 結論: **動的ルートでも `next.revalidate` は効く**。検索と詳細は別のキャッシュエントリになった（URL が違うため当然の結果。ページ違い `page=2` で別のキーになることと、`.next/cache/fetch-cache/` のファイル数の増え方の確認は、今回は実施していない）。

確認できていないこと:

- 検索の残り回数（`resources.search.remaining`）は、取得の前後で 10 のまま動かず、判定に使えなかった（原因は未調査）。キャッシュのログを根拠にした。
- 認証あり（`GITHUB_TOKEN` を設定した状態）での確認。キャッシュのキーに `Authorization` ヘッダが入るため、認証なしとは別のエントリになる（Next.js のソース `incremental-cache/index.js` のキーの作り方と、`fetch.md` 54 行目の「URL, method, headers, and body で一致」からの判断）が、実機では見ていない。人間が自分の端末で同じ手順を行うこともできる。
- 再検証時間（検索 300 秒・詳細 600 秒）を過ぎた後の挙動（古い値を返しつつ裏で取り直す）。
- 一覧の行リンクの先読み（prefetch）で GitHub の呼び出しが増えないか（ブラウザでの確認が必要）。
