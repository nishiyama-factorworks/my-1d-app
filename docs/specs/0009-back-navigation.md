# 0009: トップへの戻り導線

- Status: approved
- 作成日: 2026-10-07
- Issue: #9
- 関連: `0001-github-repo-search.md`（親仕様）、依存: 0006, 0008

## 1. 背景と目的

詳細ページからトップへ戻ったとき、直前の検索結果（キーワードとページ）が復元されるようにする。詳細ページのURLだけでも成立する（0008のAC-12）ことを保ったまま、検索条件を持ち回る。

## 2. 対象ユーザーと前提

- ロール: 閲覧者。ログイン不要。
- 前提: 0006（一覧）、0008（詳細）、0010（状態表示）が完了している。詳細ページの「トップへ戻る」は、現在は宛先が `/` で固定されている（0008）。

## 3. ユーザーストーリー

- 閲覧者として、詳細を見た後にトップへ戻ると、さっきの検索結果が同じページで見られる。それは探索を続けやすくするためである。
- 閲覧者として、詳細ページのURLを直接開いても、トップへ戻れる。それは共有されたURLからでも迷わないためである。

## 4. 範囲

### 4.1 やること

- 一覧の各行のリンクに、検索条件（`q` `page`）を詳細ページのURLのクエリとして付ける。
- 詳細ページが、URLのクエリ（`q` `page`）を読み、「トップへ戻る」の宛先を決める。
- 持ち回った値の検証と正規化（0004の関数を使う）。

### 4.2 やらないこと（Non-goals）

- ブラウザの戻るボタンの挙動の独自実装（標準の挙動に任せる）
- 404（`not-found.tsx`）の「トップへ戻る」。404 は `searchParams` を受け取れないため、0010 のとおり `/` 固定のままにする
- 詳細ページの取得（`getRepository`）の変更。検索条件は取得に使わない
- 検索条件の保存（Cookie・ストレージ・Referer の利用）

## 5. 受け入れ条件（テストに直訳できる粒度で）

> 詳細ページ・一覧の描画は、これまでと同じく `getRepository` / `searchRepositories` をモックして検証する。リンクの宛先は `href` 属性の値で検証する。

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-15a | 詳細ページを `/repos/vercel/next.js?q=react&page=3` で開いた | ページを表示する | 名前が `トップへ戻る` のリンクの `href` が `/?q=react&page=3` である |
| AC-15b | 検索を経由せず、詳細ページのURLを直接開いた（`/repos/vercel/next.js`。クエリなし） | ページを表示する | `トップへ戻る` のリンクの `href` が `/` である |
| AC-15c | 持ち回られた値が不正である（下の例） | ページを表示する | `page` は1に補正され、`q` が空なら `/` になる。外部サイトへは遷移せず、宛先は常にアプリ内のパス（`/` で始まり `//` で始まらない。スキーム・ホストを持たない）である |
| AC-15d | キーワードが `日本語 & react` | 一覧 → 詳細 → 戻る、と往復する | 一覧の行リンクの `href` に符号化して付き、詳細ページの `トップへ戻る` の `href` から `q` を読み戻すと `日本語 & react` と一致する。トップの入力欄の初期値も `日本語 & react` になる |
| AC-15e | 一覧が `q=react`、`page=3` の結果を表示している（行は `vercel/next.js`） | 一覧を表示する | 行のリンク（名前 `vercel/next.js`）の `href` が `/repos/vercel/next.js?q=react&page=3` である |
| AC-15f | 詳細ページに検索条件が付いている | ページを表示する | `getRepository` は検索条件に関係なく、これまでと同じく `owner` `repo` だけで1回呼ばれる。見出し・項目の表示も変わらない |

AC-15c の不正な値の例（`トップへ戻る` の `href` は右の値になる）:

| 詳細ページのURLのクエリ | 宛先 |
| --- | --- |
| `q=react&page=abc` | `/?q=react&page=1` |
| `q=react&page=0`、`page=-1`、`page=1e3`、`page=%203`（先頭に空白）、`page=3abc`、`page=99999999999999999999`（安全な整数でない） | `/?q=react&page=1` |
| `q=`（空）、`q=%20%20`（空白のみ）、`q=%E3%80%80`（全角空白のみ）、`page=3` のみ（`q` なし） | `/` |
| `q=` に257文字以上 | `/` |
| `q=https://evil.example/`、`q=//evil.example` | `/?q=https%3A%2F%2Fevil.example%2F&page=1`、`/?q=%2F%2Fevil.example&page=1`（キーワードとして符号化され、値の中に収まる） |
| `q=react&q=vue`（同じキーが複数） | `/?q=react&page=1`（最初の値。0004と同じ） |

## 6. 画面・API の契約

### 6.1 画面（該当する場合）

- 一覧の各行のリンク: `/repos/<owner>/<repo>?q=<q>&page=<page>`。`q` `page` は、一覧を表示しているときの（検証・正規化済みの）値。クエリの組み立ては `URLSearchParams`（キーの順序は `q`、`page`）。
- 詳細ページ（`/repos/<owner>/<repo>`）: クエリ `q` `page` を読む（任意）。`トップへ戻る` の宛先は、`q` が有効なら `/?q=<q>&page=<page>`、無ければ `/`。
- 「有効な `q`」は、0004の正規化（前後の空白除去、空は無効）を通り、かつ256文字以下のもの。`page` は0004の `parsePage` と同じ規則（正の整数表記で安全な整数。それ以外は1）。
- 404（`not-found.tsx`）とAPIエラーの表示（0010）の `トップへ戻る` は変更しない（`/`）。

### 6.2 API・Server Action（該当する場合）

該当なし。

## 7. データ

保存はしない。検索条件はURLで持ち回る。

## 8. 非機能要件

- セキュリティ: 持ち回った値は外部入力として扱い、0004の関数で検証・正規化する。宛先は `/?` で始まる固定の接頭辞に、`URLSearchParams` で符号化した値を付けて作る（0004の `buildSearchPath`）。受け取った文字列をそのままパスや `href` に使わない（オープンリダイレクトを防ぐ）。
- 詳細ページのURLの共有: 検索条件が付いたURLを共有しても、`q` `page` は戻り先を決めるだけで、詳細の内容には影響しない（AC-15f）。
- キーワードの上限（256文字）は、検索API層（`lib/github/client.ts`）の内部定数と同じ値が必要になる。重複して持つことになるため、`lib/search/` に定数を置き、一本化はIssue #20（0018）で扱う。
