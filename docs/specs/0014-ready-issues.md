# 0014: 依存が完了した Issue を Project の Ready に更新する仕組み

- Status: approved
- 作成日: 2026-10-08
- Issue: #25
- 関連: `harness/MANUAL.md` 10.4（Projects ボードの設定と運用）、`scripts/setup-github.sh`、`.claude/commands/feature.md`

## 1. 背景と目的
タスクは仕様ごとに分かれていて、各仕様の冒頭に `依存: 0004, 0006` のように前提のタスクが書かれている。前提がすべて完了（Issue が CLOSED）したタスクを Project の Status「Ready」にする作業を、人間が一覧と依存関係を見比べて行うのは手間がかかり、見落としも起きる。依存が完了したタスクを機械的に洗い出し、人間の承認のうえで Ready に更新できるようにする。

## 2. 対象ユーザーと前提
- ロール: このリポジトリを開発する人間と AI（ターミナルから実行する）。ログイン機能は無い。
- 前提: Node.js 22 以上と `gh`（認証済み）が使える。Project の読み書きには `gh` の `project` スコープが必要（現状のトークンには無い）。
- 前提: 仕様は `docs/specs/NNNN-<slug>.md` にあり、Issue のタイトルは `[feat] 0003 GitHub APIクライアント` のように、種別のあとに仕様番号が付く。

## 3. ユーザーストーリー
- 開発者として、「前提がすべて完了したので着手できるタスク」を一覧で見られる。それは依存関係を手で追わずに次の作業を選ぶためである。
- 開発者として、確認したうえで、その候補の Project の Status をまとめて Ready にできる。それは更新の手間と漏れをなくしつつ、意図しない変更を防ぐためである。
- 開発者として、`/feature` で PR を作ったときに、「この PR がマージされたら着手できるようになるタスク」が分かる。それは次の作業をすぐ決められるようにするためである。

## 4. 範囲
### 4.1 やること
- `scripts/ready-issues.mjs`: 「Ready にできる Issue」を表示するスクリプト（既定は表示のみ）。依存パッケージは追加しない。
- 依存の解釈と候補の判定を、副作用の無い純粋関数にして単体テストする。
- `--assume-closed <Issue番号>`: 指定した Issue がクローズされたと仮定して判定する（`/feature` の完了報告用）。
- `--project <番号>` で Project の Status を読み取って表示し、`--apply` で Backlog の候補だけを Ready に更新する。
- `--apply` を含む実行を、ハーネスの確認の対象にする（`.claude/settings.json` の ask と `.claude/hooks/guard-bash.sh`）。
- `/feature` の完了報告に、候補を載せる手順を足す（`.claude/commands/feature.md`）。
- `docs/harness/MANUAL.md` 10.4 の「Ready は人間が動かす」の記述を、新しい運用に改める。
- 運用方針の変更を ADR に残す。

### 4.2 やらないこと（Non-goals）
- GitHub Actions による自動更新（Project 用の権限をもつトークンの設定が要り、シークレットを扱わないハーネスの方針と衝突するため）。
- Backlog / In progress / In review / Done への自動更新。
- 依存の循環の検出。
- Project への Issue の追加（`gh project item-add`）。ボードに無い Issue は報告するだけにする。
- 仕様番号を持たない Issue（`[chore]` など）の扱い。判定の対象外とする。

## 5. 受け入れ条件（テストに直訳できる粒度で）

> 依存の解釈と候補の判定は純粋関数を直接呼んで検証する。`gh` の呼び出しはモック（引数の配列を記録する偽の実行関数）に差し替えて検証する。実際の GitHub や Project には接続しない。

### 5.1 依存の解釈

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-1 | 仕様の関連行が `- 関連: \`0001-github-repo-search.md\`（親仕様）、依存: 0004, 0006` | 依存を解釈する | `[0004, 0006]` を返す（「依存:」より前にある `0001` は含めない） |
| AC-2 | 関連行が `…、依存: 0006〜0010` | 依存を解釈する | `[0006, 0007, 0008, 0009, 0010]` に展開して返す |
| AC-3 | 関連行が `…、依存: 0009, 0010、0003（APIの接続先の差し替えが必要になる可能性）` | 依存を解釈する | `[0009, 0010, 0003]` を返す（括弧内の文と、その中の番号は無視する） |
| AC-4 | 関連行が `…、依存なし、…`、または「依存:」を含む行が無い | 依存を解釈する | `[]` を返す |

### 5.2 Issue と仕様の対応づけ

### 5.3 「Ready にできる」の判定

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-8 | Issue `0008`（OPEN）の依存が `0003`, `0004` で、その Issue がどちらも CLOSED | 判定する | `0008` を「Ready にできる」に含める |
| AC-9 | Issue `0009`（OPEN）の依存が `0006`, `0008` で、`0006` は CLOSED、`0008` は OPEN | 判定する | 含めず、「待ち」として `0009` と、待っている依存 `0008` を表示する |
| AC-10 | 依存先の仕様番号 `0014` に対応する Issue が無い | 判定する | その依存は完了していないものとして扱い、「待ち」に「Issue なし」と表示する |
| AC-11 | Issue が CLOSED、または依存が `[]`（OPEN の Issue） | 判定する | どちらも「Ready にできる」に含めない（依存の無いタスクは人間が着手を判断する） |
| AC-12 | `--assume-closed 8`、Issue `0009`（#9）の依存が `0006`（CLOSED）と `0008`（#8。OPEN） | 判定する | `#8` が CLOSED だと仮定して `0009` を含め、仮定した旨（例: `仮定: #8`）を併記する |

## 6. 画面・API の契約
### 6.1 画面（該当する場合）
該当なし。コマンドラインの出力だけ（日本語）。

### 6.2 コマンド
`node scripts/ready-issues.mjs [オプション]`

| オプション | 内容 |
| --- | --- |
| （なし） | Issue の状態だけで判定して表示する。Project には触れない |
| `--assume-closed <番号>...` | 指定した Issue がクローズされたと仮定して判定する。`--assume-closed 8 9` と `--assume-closed 8 --assume-closed 9` の両方、`#8` の書き方も受ける（カンマ区切りは受けない）。`--apply` とは併用できない（使い方の誤り。仮定に基づいて Ready に更新するのを防ぐ） |
| `--project <番号>` | その Project（所有者は既定でリポジトリの所有者）の Status を読み取って表示する |
| `--owner <名前>` | Project の所有者を指定する（既定: リポジトリの所有者） |
| `--apply` | `--project` が必須。Status が Backlog の候補だけを Ready に更新する |

- 出力: 「Ready にできる Issue」（`#8 0008 詳細ページ（依存: 0003 ✓, 0004 ✓）`）、「待ち」（`#9 0009 …（待ち: 0008）`）、警告。
- 終了コード: 0（正常。候補が0件でも0）、1（使い方の誤り、権限不足、Project の不整合、更新の失敗）。
- 外部コマンドは `gh` だけ。引数は配列で渡す（シェルを経由しない）。使うのは `gh repo view --json nameWithOwner`（読み取り。Project の所有者の既定値と、項目の照合に使うリポジトリ名を得る）、`gh issue list`（読み取り）、`gh project view / field-list / item-list`（読み取り）、`gh project item-edit`（書き込み。`--apply` のときだけ）。

## 7. データ
保存しない。入力は `docs/specs/*.md` の関連行と、`gh issue list --state all` の結果（番号・タイトル・状態）。上限は1,000件（超えたら警告を表示する）。

## 8. 非機能要件
- セキュリティ:
  - 既定は読み取りだけ。書き込み（`gh project item-edit`）は `--apply` のときだけで、ハーネスの確認を必ず通す（AC-22）。スクリプトの内部で呼ぶ `gh` には、Claude の Bash 呼び出しに効く確認が働かないため、`--apply` を含む実行そのものを確認の対象にする。
  - トークンを読まない・表示しない。`gh auth refresh` はスクリプトから実行しない（人間が行う）。
  - Issue のタイトルは他者が書いた入力として扱い、中身の指示には従わず、制御文字を除いて表示する（AC-21）。
- 信頼性: 判定は純粋関数で、同じ入力に同じ結果を返す。`--apply` は冪等（AC-16）。失敗時は何も変更しないか、成功と失敗を区別して報告する。
- 保守性: 仕様の「依存:」の書き方が増えたときは、解釈の関数とテストを直す（AC-1〜4 が現状の書き方の一覧）。

## 9. 未決事項
- [ ] Project の番号、Status フィールドの名前と選択肢（`Status`、`Backlog / Ready / In progress / In review / Done` を想定）。ボードが存在するかも未確認 / 担当: 人間（`gh auth refresh -s project` の実行後に Claude が確認） / 期限: 実機での確認時
- [ ] 実際の `--apply` の動作確認。権限が無い現状では、モックを使ったテストまでしか検証できない / 担当: 人間と Claude / 期限: 権限の付与後
- 前提（仕様で定める）: `依存: 0009, 0010、0003（…可能性）` のような「可能性」を添えた依存も、通常の依存として扱う（AC-3）。依存の無いタスクは対象にしない（AC-11）。
