## 1. 背景と目的
検索から詳細、戻りまでの一連の流れを、実際のブラウザで確認する。単体・コンポーネントテストでは見つけにくい、画面遷移とURLの結合部分の不具合を検出する。

## 2. 対象ユーザーと前提
- ロール: 開発者・評価者。
- 前提: 0009と0010が完了している。実際のGitHub APIには接続しない（不安定でレート制限があるため）。

## 3. ユーザーストーリー
- 開発者として、主要な操作の流れを自動で確認できる。それは変更時の回帰を早く見つけるためである。

## 4. 範囲
### 4.1 やること
- Playwrightの導入と、`pnpm test:e2e` の追加
- 主要シナリオ2本
- GitHub APIの偽物（モックサーバー等）への差し替え
- CIでの実行可否の判断（`RUN_E2E` 変数で有効化する想定）

### 4.2 やらないこと（Non-goals）
- 実際のGitHub APIへの接続

## 5. 受け入れ条件（テストに直訳できる粒度で）

> GitHub APIは偽物に差し替えて実行する。

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-31a | 偽のAPIが `react` の検索結果（複数ページ分）と詳細を返す | トップで `react` を入力して検索 → 一覧の1件を選ぶ → 詳細の「トップへ戻る」を押す | 一覧が表示され、詳細が表示され、戻ると同じキーワード・同じページの検索結果が復元される |
| AC-31b | 偽のAPIが `total_count=0` の検索結果を返す | トップで存在しないキーワードを入力して検索する | 0件の表示（「見つかりませんでした」）が出る |

## 6. 画面・API の契約
### 6.1 画面（該当する場合）
新しい画面はない。

### 6.2 API・Server Action（該当する場合）
サーバー側でGitHub APIを呼ぶため、Playwrightのリクエスト差し替えでは偽物に切り替えられない。APIのベースURLを環境変数で上書きできるようにするか、別の方法で偽のAPIを用意する必要がある（9節）。

## 7. データ
該当なし。E2E用の偽のAPIレスポンスを用意する。

## 8. 非機能要件
- 安定性: 外部サービスに依存せず、毎回同じ結果になる。
- 実行時間: CIで許容できる範囲にする。重い場合は `RUN_E2E` で任意実行にする。
