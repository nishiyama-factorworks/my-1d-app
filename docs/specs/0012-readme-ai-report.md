## 1. 背景と目的

課題の提出物として、READMEを書く。READMEの主な役割は、課題にある「工夫した点やこだわったポイント、なぜその選択をしたのかなどを文章でまとめる」ことである（2026-10-09 人間が決定）。そのため、セットアップ・構成・範囲と制約は外部ファイル（`docs/`）に移し、READMEには要約と参照だけを置く。AIを利用した方法のレポートはREADMEに含める。

## 2. 対象ユーザーと前提

- ロール: 評価者、およびこのリポジトリを初めて見る開発者。
- 前提: 0011までの実装が完了している。計画・ADRで記録した判断が参照できる。`pnpm dev` / `pnpm start`（0020）と `pnpm test:e2e`（0013）が使える。
- 言語は**日本語**（課題文と `CLAUDE.md` に合わせる。2026-10-09 人間が決定）。

## 3. ユーザーストーリー

- 評価者として、READMEを読むだけで、アプリの概要と、工夫した点とその選択の理由が分かる。それは設計の考え方を評価するためである。
- 評価者として、動かし方や構成、範囲と制約の詳細が必要なときは、READMEの要約から該当の文書へ進める。それは評価のために手早く動かして確認するためである。
- 評価者として、AIをどう使ったかが分かる。それはAI活用の方法と人間の判断を評価するためである。

## 4. 範囲

### 4.1 やること

- `README.md` の再構成。次の6つの節（`##` 見出し）を、この名前と順で置く。「工夫した点と理由」を READMEの主役として概要の直後に置く。
  1. `## 概要`
  2. `## 工夫した点と理由`（`###` で、次の7つ）
     - 「Watcher数の取得元」
     - 「GitHub APIをサーバー側だけで呼ぶ」
     - 「検索条件をURLで持つ」
     - 「1,000件の上限の扱い」
     - 「取得結果のキャッシュ」
     - 「エラーを状態として見せる」
     - 「テストの検出力を確かめる」
  3. `## セットアップ`（要約と `docs/setup.md` への参照）
  4. `## 構成`（要約と `docs/structure.md` への参照）
  5. `## 範囲と制約`（要約と `docs/scope.md` への参照）
  6. `## AI利用レポート`（`###` で「AI利用について考慮した点」「使ったツール」「進め方」「人間が判断・修正した点」「AIの出力で注意した点」）
- 外部ファイル3つの新規作成。内容は現在の README の該当節を移し、READMEの「セットアップ」「構成と判断のうちの画面構成とルーティング・ディレクトリ構成」「範囲と制約」の詳細をここに置く。見出しは次のとおりに固定する。
  - `docs/setup.md`: `#` 見出し「セットアップ」、`##` で「前提」「手順」「テスト」「環境変数」
  - `docs/structure.md`: `#` 見出し「構成」、`##` で「画面構成とルーティング」「ディレクトリ構成」
  - `docs/scope.md`: `#` 見出し「範囲と制約」、`##` で「プロダクション想定の範囲」「対応しなかった事項」「既知の制約」
- 「工夫した点と理由」は、現在の5つの項目に、「エラーを状態として見せる」「テストの検出力を確かめる」を足した7つにし、それぞれ「何を」「なぜ（理由）」「代わりに考えた案やトレードオフ」を文章で書く。根拠として仕様・計画・ADR・PRへの相対リンクを張る。
- 「AI利用について考慮した点」は、人間が追記した3点（基本的にAIに作業させることに注力する、タスクを細かく細分化して機能を積み上げる、まずGitHub+AIをフル活用したワークフローを作る）を残し、仕様・計画・PRで確認できる実例で加筆訂正する（人間の意図は変えない）。「使ったツール」から Co-Authored-By のモデル名の記述を人間が削除したため、戻さない。
- 計画・ADRで記録した判断の、READMEへの反映（根拠として仕様・計画・ADRへ相対リンクを張る）
- READMEと外部ファイル3つの構造を検査するテスト（`tests/docs/readme.test.ts`）の更新。テスト以外のコード（`app/` `features/` `lib/` など）は変更しない。
- AI利用レポートは README の節として書く（約1〜2画面。2026-10-09 人間が決定）。事実は git 履歴・仕様・計画・ADR・PR で確認できるものだけを書き、PR 番号・仕様番号・ADR 番号で根拠を示す。

### 4.2 やらないこと（Non-goals）

- アプリのコード（`app/` `features/` `lib/` `components/`）の変更（READMEの記述で食い違いに気づいたら、別タスクで直す）
- AI利用レポートを別ファイルに分けること（READMEに残す。2026-10-09 人間が決定）
- 英語版のREADME
- スクリーンショットの掲載
- トークンの値、個人情報、内部パスなどの秘密情報を書くこと
- `docs/architecture.md`（設計の記録）の内容の変更

## 8. 非機能要件

- 正確性: READMEと外部ファイルの記述は実装・仕様・ADRと食い違わない。食い違いが見つかった場合は、仕様とコードのどちらが正しいかを判断し、直す。コードの修正が必要なら、別タスクにする（4.2）。
- 秘密情報（トークンの値など）を書かない（AC-30g）。
- 確認できていないことは断定しない。数値（件数、PR数、テスト数など）は、書く時点で `git log` やテストの実行結果で確認した値だけを書く。
- 外部ファイルへ移す内容は、意味を変えずに移す（事実の食い違いを新たに作らない）。移した後、READMEと外部ファイルに同じ内容を重複して書かない（READMEは要約と参照だけ）。
