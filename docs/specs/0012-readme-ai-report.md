## 1. 背景と目的

課題の提出物として、READMEを書く。READMEの主な役割は、課題にある「工夫した点やこだわったポイント、なぜその選択をしたのかなどを文章でまとめる」ことである（2026-10-09 人間が決定）。そのため、構成・範囲と制約・セットアップの詳細は外部ファイル（`docs/`）に移し、READMEには要約と参照だけを置く。AIを利用した方法のレポートはREADMEに含める。

READMEは、技術選考課題の提出物として、初見の評価者（社外の人）が読む。次の点を満たすように、2026-10-09 に見直した（人間の依頼）。

- 評価者が、動かすまで・課題の要求への答え・工夫した点に、最短でたどり着ける（目次、クイックスタート、要件との対応、テストの全体像）。
- AI利用レポートが、課題文の「AIを利用した場合は利用方法のレポートをREADMEにまとめてください」に、外部の読者向けに自己完結した形で答える（内部の番号や独自の用語に頼らない。応募者本人の判断・理解と、AIの効果・限界が見える）。

## 2. 対象ユーザーと前提

- ロール: 評価者（社外の人を含む）、およびこのリポジトリを初めて見る開発者。
- 前提: 0011までの実装が完了している。計画・ADRで記録した判断が参照できる。`pnpm dev` / `pnpm start`（0020）と `pnpm test:e2e`（0013）が使える。
- 言語は**日本語**（課題文と `CLAUDE.md` に合わせる。2026-10-09 人間が決定）。

## 3. ユーザーストーリー

- 評価者として、READMEを開いてすぐに、アプリの概要と動かし方、課題の要求にどう答えたかが分かる。それは限られた時間で評価するためである。
- 評価者として、工夫した点と、その選択の理由が分かる。それは設計の考え方を評価するためである。
- 評価者として、AIをどう使い、応募者が何を自分で判断・理解したかが分かる。それはAI活用の方法と、応募者本人の力量を評価するためである。

## 4. 範囲

### 4.1 やること

- `README.md` の再構成。冒頭（`#` 見出しの直後、最初の `##` の前）に**目次**（各 `##` 節へのアンカーリンクの一覧。見出しは付けない）を置き、次の8つの節（`##` 見出し）を、この名前と順で置く。「工夫した点と理由」を READMEの主役とする。
  1. `## 概要`
  2. `## セットアップ`（クイックスタート: `pnpm install` と `pnpm dev`、`GITHUB_TOKEN` は任意であること、`docs/setup.md` への参照）
  3. `## 課題の要件との対応`（表。課題文の要求ごとに、READMEの節や `docs/` のファイルへの参照を付ける。4.1.1）
  4. `## 工夫した点と理由`（`###` で、次の7つ）
     - 「Watcher数の取得元」
     - 「GitHub APIをサーバー側だけで呼ぶ」
     - 「検索条件をURLで持つ」
     - 「1,000件の上限の扱い」
     - 「取得結果のキャッシュ」
     - 「エラーを状態として見せる」
     - 「テストの検出力を確かめる」
  5. `## テスト`（テストの全体像。4.1.2）
  6. `## 構成`（要約と `docs/structure.md` への参照）
  7. `## 範囲と制約`（要約と `docs/scope.md` への参照）
  8. `## AI利用レポート`（`###` で、次の6つ）
     - 「AI利用について考慮した点」
     - 「使ったツールと任せた範囲」
     - 「進め方」
     - 「自分で判断・理解した点」
     - 「AIの出力で注意した点」
     - 「効果と限界、次にやるなら」
- **4.1.1 課題の要件との対応**: 表の行は、課題文の次の9項目（この名前で）。各行の「対応」の列に、実装や文書への参照（READMEの節へのアンカーリンク、`docs/` のリンク、または実在するバッククォート内のパス）を付ける。
  - 「キーワード検索と一覧」「詳細の表示項目」「詳細はページ（モーダルでない）」「ページネーション」「テストコード」「プロダクション想定」「見やすさ・操作しやすさ」「AI利用レポート」「工夫した点の説明」
- **4.1.2 テスト**: 次を、READMEの要約として書く。詳細な実行手順は `docs/setup.md` に任せる（重複させない）。
  - テストの種類: 単体・結合（Vitest + Testing Library）、構造検査（ディレクトリ構成・文書・設定の検査）、アクセシビリティの検査、E2E（Playwright。任意で、偽のGitHub APIに差し替えて実行）
  - 実行コマンド: `pnpm test`、`pnpm test:e2e`、`bash scripts/verify.sh`
  - 方針: 受け入れ条件から先にテストを書く、実際のGitHub APIに依存しない、変異で検出力を確かめる（詳細は「工夫した点と理由」の「テストの検出力を確かめる」へのリンク）
  - テスト件数を書く場合は、書く時点の `pnpm test` の結果と日付を添える。
- 外部ファイル3つ（`docs/setup.md`・`docs/structure.md`・`docs/scope.md`）は、すでに作成済みで、内容と見出しは変えない。見出しは次のとおり。
  - `docs/setup.md`: `#` 見出し「セットアップ」、`##` で「前提」「手順」「テスト」「環境変数」
  - `docs/structure.md`: `#` 見出し「構成」、`##` で「画面構成とルーティング」「ディレクトリ構成」
  - `docs/scope.md`: `#` 見出し「範囲と制約」、`##` で「プロダクション想定の範囲」「対応しなかった事項」「既知の制約」
- 「工夫した点と理由」は7つの小節で、それぞれ「何を」「なぜ（理由）」「代わりに考えた案やトレードオフ」を文章で書く。根拠として仕様・計画・ADR・PRへの相対リンクを張る。各小節の最初の1〜2文で要点が分かるように書く。
- **AI利用レポートの書き方**（外部の読者向けに自己完結させる）:
  - 内部の番号（仕様・計画・ADR・PR・Issue）は、文の主役にせず、括弧書きの根拠として添える。内部の識別子（`AC-3` のような受け入れ条件の ID）は使わない。
  - READMEで使う独自の用語（受け入れ条件、ハーネス、変異、RED/GREEN、サブエージェント）は、最初に出てくる場所で一言説明する。
  - README自身の改訂の経緯（「この README」「Draft PR #39 を見た人間が」など）と、PR数・仕様数などの件数の羅列は書かない。
  - 「AI利用について考慮した点」の人間が追記した3点の文は、意図を変えずに残す。
  - 「使ったツールと任せた範囲」には、Claude Code と、コミットの Co-Authored-By に残っているモデル名（Claude Opus 5.5、Claude Sonnet 5.5）、AIに任せた工程、人間が担った工程を書く（2026-10-09 人間が「モデル名は戻す」と決定）。
  - 「自分で判断・理解した点」は**一人称**（私は〜）で書く。リポジトリの記録（仕様・計画・PRの変更履歴）で確認できる、人間が実際に決めたことを案としてAIが作り、人間が直して承認した文だけを載せる。「どこまで自分で読んで理解しているか」は、人間の言葉で書く。
  - 「効果と限界、次にやるなら」には、AIを使って良かった点、うまくいかなかった点（限界）、次に同じことをするならどうするか、を書く。
  - 分量は約1画面強に収める（AC-30j）。
- READMEと外部ファイルの構造を検査するテスト（`tests/docs/readme.test.ts`）の更新。テスト以外のコード（`app/` `features/` `lib/` など）は変更しない。
- 事実は git 履歴・仕様・計画・ADR・PR で確認できるものだけを書く。

### 4.2 やらないこと（Non-goals）

- アプリのコード（`app/` `features/` `lib/` `components/`）の変更（READMEの記述で食い違いに気づいたら、別タスクで直す）
- AI利用レポートを別ファイルに分けること（READMEに残す。2026-10-09 人間が決定）
- 英語版のREADME
- スクリーンショットの掲載
- トークンの値、個人情報、内部パスなどの秘密情報を書くこと
- `docs/architecture.md`（設計の記録）の内容の変更
- 「工夫した点と理由」に、7つ以外の小節（操作しやすさ、技術選定の理由など）を足すこと（今回は扱わない。必要なら別の改訂にする）

## 8. 非機能要件

- 正確性: READMEと外部ファイルの記述は実装・仕様・ADRと食い違わない。食い違いが見つかった場合は、仕様とコードのどちらが正しいかを判断し、直す。コードの修正が必要なら、別タスクにする（4.2）。
- 秘密情報（トークンの値など）を書かない（AC-30g）。
- 確認できていないことは断定しない。数値（件数、PR数、テスト数など）は、書く時点で `git log` やテストの実行結果で確認した値だけを書く。
- 外部ファイルへ移した内容は、READMEと重複して書かない（READMEは要約と参照だけ）。
- 応募者本人の考え（「自分で判断・理解した点」）は、AIが事実から作った案を、人間が直して承認した文だけを載せる。人間が確認していない内容を、本人の考えとして載せない。
