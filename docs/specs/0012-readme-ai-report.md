- Status: approved

## 1. 背景と目的

課題の提出物として、READMEを書く。工夫した点、こだわったポイント、その選択をした理由を文章でまとめ、AIを利用した方法のレポートを含める。

## 2. 対象ユーザーと前提

- ロール: 評価者、およびこのリポジトリを初めて見る開発者。
- 前提: 0011までの実装が完了している。計画・ADRで記録した判断が参照できる。`pnpm dev` / `pnpm start`（0020）と `pnpm test:e2e`（0013）が使える。
- 言語は**日本語**（課題文と `CLAUDE.md` に合わせる。2026-10-09 人間が決定）。

## 3. ユーザーストーリー

- 評価者として、READMEを読むだけで、アプリの概要と動かし方が分かる。それは評価のために手早く動かして確認するためである。
- 評価者として、工夫した点と、その選択の理由が分かる。それは設計の考え方を評価するためである。
- 評価者として、AIをどう使ったかが分かる。それはAI活用の方法と人間の判断を評価するためである。

## 4. 範囲

### 4.1 やること

- `README.md` の執筆（現在は `# my-1d-app` の1行だけ）。次の5つの節（`##` 見出し）を、この名前と順で置く。
  1. `## 概要`
  2. `## セットアップ`
  3. `## 構成と判断`（`###` で「画面構成とルーティング」「ディレクトリ構成」「工夫した点と理由」）
  4. `## 範囲と制約`（`###` で「プロダクション想定の範囲」「対応しなかった事項」「既知の制約」）
  5. `## AI利用レポート`（`###` で「使ったツール」「進め方」「人間が判断・修正した点」「AIの出力で注意した点」）
- 計画・ADRで記録した判断の、READMEへの反映（根拠として仕様・計画・ADRへ相対リンクを張る）
- READMEの構造を検査するテスト（`tests/docs/readme.test.ts`）の追加。テスト以外のコード（`app/` `features/` `lib/` など）は変更しない。
- AI利用レポートは README の節として書く（約1〜2画面。2026-10-09 人間が決定）。事実は git 履歴・仕様・計画・ADR・PR で確認できるものだけを書き、PR 番号・仕様番号・ADR 番号で根拠を示す。

### 4.2 やらないこと（Non-goals）

- アプリのコード（`app/` `features/` `lib/` `components/`）の変更（READMEの記述で食い違いに気づいたら、別タスクで直す）
- AI利用レポートを別ファイルに分けること
- 英語版のREADME
- スクリーンショットの掲載
- トークンの値、個人情報、内部パスなどの秘密情報を書くこと

## 8. 非機能要件

- 正確性: READMEの記述は実装・仕様・ADRと食い違わない。食い違いが見つかった場合は、仕様とコードのどちらが正しいかを判断し、直す。コードの修正が必要なら、別タスクにする（4.2）。
- 秘密情報（トークンの値など）を書かない（AC-30g）。
- 確認できていないことは断定しない。数値（件数、PR数、テスト数など）は、書く時点で `git log` やテストの実行結果で確認した値だけを書く。
