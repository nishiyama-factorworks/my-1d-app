## 1. 背景と目的
選考課題として、GitHubのリポジトリをキーワードで検索し、一覧から選んだリポジトリの詳細（Star数など）を別ページで確認できるWebアプリを、Next.js（App Router）で作る。プロダクション品質を意識して実装し、工夫点とAI利用方法をREADMEにまとめて提出する。

このファイルは全体の目的・決定事項・タスク分割・ACの担当表を持つ。受け入れ条件（Given/When/Then）の詳細は各タスク仕様に置く。

## 2. 対象ユーザーと前提
- ロール: GitHubのリポジトリを探したい閲覧者。ログイン不要。
- 利用環境: モダンブラウザ。PCを主とし、狭い画面幅でも表示が崩れない程度に対応する。

決定事項:

| 項目 | 決定 |

| フレームワーク | Next.js v16以降 / App Router |
| 言語 | TypeScript（strict） |
| データ取得元 | GitHub REST API（`search/repositories` と `repos/{owner}/{repo}`） |
| デプロイ | 不要（提出物はリポジトリのみ） |
| 開発運用 | PR運用。1タスク = 1 Issue = 1ブランチ = 1 PR。最初はDraft PR、CI緑で人間がReady化・マージ（ハーネスMANUAL 10章） |

| コンポーネントライブラリ・CSS手法 | 未決。0002の計画で決め、必要ならADRに記録する |

## 3. ユーザーストーリー
- 閲覧者として、キーワードでGitHubのリポジトリを検索できる。それは目的のリポジトリを探すためである。
- 閲覧者として、検索結果を30件ずつページを移動しながら見られる。それは多数の結果から探しやすくするためである。
- 閲覧者として、結果から1件を選び、Star数・Watcher数・Fork数・Issue数・言語を別ページで確認できる。それはリポジトリの活発さや規模を判断するためである。
- 閲覧者として、詳細ページから検索結果に戻れる。それは探索を続けやすくするためである。
- 評価者として、仕様・テスト・READMEから設計意図を追える。それは実装の品質を判断するためである。

## 4. 範囲
### 4.1 やること
- 検索ページ（トップ）と詳細ページの2画面
- 検索、一覧表示、ページネーション、詳細表示、トップへの戻り導線
- 読み込み中・0件・各種エラーの表示
- テストコード、READMEの記述（工夫点、選択理由、AI利用レポート）

### 4.2 やらないこと（Non-goals）
- ソート順の切り替え（APIの既定＝ベストマッチのまま）
- 無限スクロール、入力途中の逐次検索
- 認証・ログイン、お気に入り等のユーザー固有機能
- デプロイ、独自ドメイン、監視
- ダークモード、多言語切り替え、対応ブラウザ範囲の個別保証

## 6. 画面・API の契約
### 6.1 画面（該当する場合）

| 画面 | パス | 表示要素 |
| --- | --- | --- |
| トップ（検索） | `/?q=<keyword>&page=<n>` | タイトル、検索ボックス、検索ボタン、結果一覧、総ヒット件数、ページネーション |
| 詳細 | `/repos/<owner>/<repo>` | タイトル、オーナーアイコン、リポジトリ名、オーナー名、言語、Star数、Watcher数、Fork数、Issue数、GitHub本体へのリンク、トップへ戻るリンク |

状態ごとの表示（読み込み中 / 0件 / エラー / 404 / 範囲外ページ）は、0007と0010で定める。詳細からトップへ戻るときに検索条件を持ち回る方法は、0009の計画で決める。

### 6.2 API・Server Action（該当する場合）
自前のAPIは持たない。サーバー側（Server Component / Route Handler）から、次のGitHub REST APIを呼ぶ（0003）。

| 用途 | エンドポイント | 備考 |
| --- | --- | --- |
| 検索 | `GET /search/repositories` | `q` `page` `per_page=30`。`sort` `order` は送らない。上位1,000件まで |
| 詳細 | `GET /repos/{owner}/{repo}` | Watcher数に `subscribers_count` を使う |

エラーは `RATE_LIMIT` `NOT_FOUND` `VALIDATION` `UPSTREAM` `NETWORK` の5種別に分類する（0003）。

## 7. データ
データの保存・永続化はしない（DBなし）。アプリ内で扱う項目と、GitHub APIの項目の対応は次のとおり。型は0003で定義し、以降のタスクはこの型だけを使う。

| アプリ内の項目 | 検索API（一覧用） | リポジトリ個別API（詳細用） |
| --- | --- | --- |
| リポジトリ名（`owner/repo`） | `full_name` | `full_name` |
| オーナー名 | `owner.login` | `owner.login` |
| オーナーアイコンURL | `owner.avatar_url` | `owner.avatar_url` |
| 言語（nullあり） | — | `language` |
| Star数 | — | `stargazers_count` |
| Watcher数 | 使わない（`watchers_count` はStar数と同値のため） | `subscribers_count` |
| Fork数 | — | `forks_count` |
| Issue数 | — | `open_issues_count` |
| GitHub本体URL | — | `html_url` |
| 総ヒット件数 | `total_count` | — |

## 8. 非機能要件
「プロダクション想定」は、次の範囲を満たすことと定義する（READMEにも明記する）。担当タスクを括弧内に示す。

- **セキュリティ**: GitHub APIの呼び出しはサーバー側で行う。トークンは環境変数で受け取りクライアントに露出させない。トークンが無くても動作する。URLクエリなど外部入力は検証して扱う（0003, 0004）。
- **信頼性**: 全APIエラーを握りつぶさず、状態表示として表現する（0003, 0010）。
- **アクセシビリティ**: フォーム要素のラベル、キーボード操作、画像の代替テキスト（0011）。
- **パフォーマンス**: 取得結果のキャッシュ方針を決める。不要なクライアントJSを増やさない（0011）。
- **見やすさ**: 狭い画面幅でも崩れない程度のレスポンシブ対応（0011）。
- **メタデータ**: ページタイトルを画面ごとに設定する（0011）。
- **品質ゲート**: 型チェック、Lint、テスト、ビルドが `scripts/verify.sh` とCIで通る（全タスク共通）。
- **テスト方針**: Vitest + Testing Libraryを軸にする。API呼び出しはモックし、実際のGitHub APIには依存しない。E2E（Playwright）は任意（0013）。
