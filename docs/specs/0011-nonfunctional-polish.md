# 0011: 非機能の仕上げ（アクセシビリティ・レスポンシブ・メタデータ・キャッシュ）

- Status: approved
- 作成日: 2026-10-07
- Issue: #11
- 関連: `0001-github-repo-search.md`（親仕様、8節の非機能要件）、依存: 0006〜0010

## 1. 背景と目的

機能がそろった後に、「プロダクション想定」の非機能要件（0001の8節）を満たすように仕上げる。アクセシビリティ、レスポンシブ、ページタイトル、キャッシュ方針を対象とする。

2026-10-08 時点のコードを調べた結果、AC-26a は満たしており、AC-26b〜26d・AC-27 は部分的、AC-28・AC-29 は未達である（現状の詳細は計画に記録する）。

## 2. 対象ユーザーと前提

- ロール: 閲覧者（キーボード操作や支援技術の利用者、スマホの利用者を含む）。
- 前提: 0006〜0010が完了し、全画面と全状態が実装済みである。アプリ名は仮の定数 `APP_NAME`（`lib/app-config.ts`、`GitHub リポジトリ検索`）を使う。

## 3. ユーザーストーリー

- 閲覧者として、キーボードだけで検索から詳細の確認まで操作できる。それはマウスを使えない場合でも使えるようにするためである。
- 閲覧者として、スマホなどの狭い画面でも崩れずに使える。それは端末を選ばず使えるようにするためである。
- 閲覧者として、ブラウザのタブから、今どの画面か分かる。それは複数タブを開いても迷わないためである。
- 評価者として、取得結果のキャッシュ方針と理由を確認できる。それはプロダクション想定の判断を評価するためである。

## 4. 範囲

### 4.1 やること

- 全画面のアクセシビリティの点検と修正（0件・範囲外の `role`、独立した画面の見出し、`lang`）
- 狭い画面幅での表示崩れの修正（折り返しの指定が無い箇所）
- ページごとのタイトル設定（ルートの `title` の構造と `lang` を含む。Issue #17 / 仕様 0017 から、`metadata` と `lang` の範囲を移す）
- キャッシュ方針の決定と実装（検索・詳細の取得に再検証時間を設定する）

### 4.2 やらないこと（Non-goals）

- 凝ったデザイン、アニメーション
- ダークモード、多言語対応
- 自動アクセシビリティチェックのツール（jest-axe 等）の導入。依存を増やさない。確認は Testing Library の `role` / ラベルによる検索、`eslint-config-next` 経由の `jsx-a11y`、目視で行う
- 一覧の行全体をクリック可能にする、ページ移動後のフォーカス管理、再試行中の表示、ページ番号リンクの `aria-label`、外部リンクの補足（過去の計画で 0011 に送られた任意の改善案。AC に必要ないため行わない）
- 詳細ページのタイトルのための追加の API 呼び出し（タイトルは URL の `params` から作る）
- キャッシュコンポーネント（`cacheComponents` / `"use cache"`）の導入、セキュリティヘッダ（CSP 等）、画像最適化の負荷対策、IP 単位のレート制限

## 6. 画面・API の契約

### 6.1 画面（該当する場合）

新しい画面はない。全画面（トップ、詳細、各状態）の見た目・操作性を調整する。

- ページタイトルの形式は5節のAC-28のとおり。トップは `generateMetadata({ searchParams })`、詳細は `generateMetadata({ params })` で作る。ルートレイアウトの `template` は同じセグメントの `page.tsx`（トップ）には適用されないため、トップのタイトルは `title.absolute` で完成形（`<q> の検索結果 | <アプリ名>`）を返す。詳細は子のセグメントなので `template` が適用され、`title` は `<owner>/<repo>` を返す。
- 存在しないリポジトリの 404 でも、タイトルはURLの `params` 由来（`<owner>/<repo> | <アプリ名>`）になる。
- 独立した画面の見出し（AC-26c1）: `app/error.tsx` と詳細のAPIエラー分岐には現在 `h1` が無い。次の `h1` を足す（文言は仮。計画の承認で確定する）。
  - `app/error.tsx`: `エラーが発生しました`
  - 詳細のAPIエラー分岐: `リポジトリを表示できませんでした`
  - トップのAPIエラー、0件、範囲外ページは、ページの `h1`（アプリ名）がすでにある。
  - 読み込み中（`loading`）は一時的な表示で、`role="status"` だけとする（`h1` は不要）。
- 0件と範囲外の案内: 既存の文言は変えず、`role="status"` を付ける。
- 狭い画面: 0件の案内の文言（キーワードを含む）に折り返しの指定（`break-all` など）を付ける。他の画面は、既存の指定（0005〜0008）で足りることを目視で確認する。
- フォーカス: ブラウザ既定のフォーカス表示を使い、消さない。独自のスタイルは足さない。

### 6.2 API・Server Action（該当する場合）

該当なし。取得時の再検証設定のみを扱う。`lib/github/http.ts` の `fetch` に `next: { revalidate: <秒> }` を渡す（検索用と詳細用で値を分ける）。公開インターフェース（`searchRepositories` `getRepository`）は変えない。

## 7. データ

保存はしない。取得結果のキャッシュの再検証時間を設定する（値は計画で決める）。キャッシュされるのは、`GITHUB_TOKEN` で取得した公開リポジトリの情報だけである（非公開と確認できないリポジトリは0003で返さない）。HTTPステータスが200以外の応答はキャッシュされない（Next.js の仕様）。

## 8. 非機能要件

- アクセシビリティ: 5節のAC-26のとおり。自動チェックツール（jest-axe 等）は導入しない（4.2）。
- レスポンシブ: 目視確認でよい。確認した幅と結果をPRに書く（AC-27）。
- パフォーマンス: 不要なクライアントJSを増やさない。
- キャッシュ: 認証なしの検索は1分10回、コアAPIは1時間60回に制限される（過去の計画での実測・記述）ため、同じ取得の繰り返しでレート制限を使い切らないようにするのが目的。動的ルートで `next.revalidate` が実際に効くかは、ドキュメントに明記が無い。計画で実機確認の手順を決め、結果をADRに記録する。
- 先読み（prefetch）: 一覧の行リンクのプリフェッチで取得が増えないかを、計画の手動確認に含める（0006〜0009の申し送り）。
