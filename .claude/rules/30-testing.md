# テストルール（TDD）

## 基本

- テストは**仕様（受け入れ条件）から**書く。実装の内部構造ではなく、外から観測できる振る舞いを検証する。
- テスト名は日本語で「〜のとき〜になる」と読める文にし、`AC-<番号>` を含める。例: `AC-2: 在庫が0のとき購入ボタンが無効になる`
- 1 テスト 1 関心事。Arrange / Act / Assert の 3 区画が見分けられる構造にする。
- テスト間で状態を共有しない。順序依存・時刻依存・乱数依存を作らない（必要なら固定化する）。

## 配置

- 単体/コンポーネントテストは対象と同じディレクトリに `*.test.ts(x)` として置く。
- E2E は `e2e/`（または `tests/e2e/`）。**主要な利用シナリオだけ**に絞る（遅く壊れやすいため）。

## 何をテストするか

- 純粋ロジック（変換・計算・検証）: 単体テスト。入力の境界値・異常値を含める。
- コンポーネント: Testing Library で**ユーザー視点**（role / label / text）で検索する。`data-testid` は最後の手段。実装詳細（state、内部関数）を直接検証しない。
- Server Action / Route Handler: 入力検証エラー・認可エラー・正常系を検証する。
- E2E: ログインして購入完了など、価値の高い一連の流れ。

## モック方針

- モックするのは**プロセス境界の外**（ネットワーク、DB、時刻、外部サービス）だけ。自分たちのモジュール同士をむやみにモックしない。
- モックが多すぎるテストは設計の合図。責務の分割を見直す。

## 禁止事項

- 実装を通すためにテストの期待値を弱める/削除する/`skip`・`only` を残す。
- カバレッジ数値だけを目的とした、何も検証しないテスト。
- 失敗の再現を確認せずに書いたテスト（RED を確認する）。
- テストが落ちたときに実装を直さず、テスト側を変更して通す。期待値の変更が必要なら、仕様変更の根拠を報告に書く。
