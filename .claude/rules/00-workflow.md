# 開発ワークフロー詳細（仕様駆動 + TDD）

CLAUDE.md の「4. 開発ワークフロー」の詳細版。常時読み込まれる。

## タスクの大きさ

- 1タスク = 1コミットで説明できる大きさ（目安: 変更ファイル 5 以下、差分 300 行以下）。
- 大きい場合は計画段階（`docs/plans/`）で分割する。分割できない大きさなら、先に人間へ相談する。

## RED → GREEN → REFACTOR の運用

- RED: 受け入れ条件 1 つにつき、最低 1 つのテストを書く。テスト名に `AC-<番号>` を含めると仕様との対応が追える。
- RED を必ず**実行して失敗を確認**する。「失敗する理由」が意図どおり（未実装による失敗）であることを見る。構文エラーやインポートエラーでの失敗は RED と認めない。
- GREEN: そのテストを通す**最小限**の実装。先回りの抽象化・未使用の引数・将来用の分岐を入れない。
- REFACTOR: 緑を保ったまま重複排除・命名改善。振る舞いを変えない。
- テストを書きづらいときは設計を疑う（副作用を境界に寄せ、純粋関数に切り出す）。

## 質問すべき場面（実装を止めて人間に聞く）

- 受け入れ条件が曖昧、または複数の解釈ができる。
- 仕様と既存コード/既存テストが矛盾している。
- 依存パッケージの追加、DB スキーマ変更、認証・認可の方針に関わる変更。
- 検証が 3 回連続で同じ理由で失敗し、原因が特定できない。

## 報告の形式

作業完了時は次の順で簡潔に報告する。

1. 何を実装/修正したか（仕様の AC 番号と対応づけて）
2. 追加/変更したテスト
3. `bash scripts/verify.sh` の結果（PASS/FAIL を事実のまま）
4. 未解決事項・判断を仰ぎたい点

## 中断・再開

- 作業が長引く場合、`docs/plans/<計画>.md` の `Status:` と各タスクのチェックボックスを更新してから止める。
- 再開時は SessionStart で表示される「進行中の計画」を最初に読む。
