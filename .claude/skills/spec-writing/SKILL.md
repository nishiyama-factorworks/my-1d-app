# 仕様書の書き方（spec-writing）

仕様は「あとでテストになる文章」。曖昧さは実装の手戻りに直結するため、書く前に潰す。

## 手順

1. **要望を分解**する: 誰が（ユーザー）・何をしたくて（目的）・どうなれば成功か（成功基準）。
2. **既存を調べる**: `docs/specs/` に近い仕様がないか、`src/` に再利用できる実装がないかを確認する。
3. **不明点を洗い出す**: 下の「確認チェックリスト」を埋め、埋まらない項目は「未決事項」に残すか人間に質問する。**推測で埋めない。**
4. `docs/specs/_template.md` をコピーし、連番 `NNNN-<slug>.md` で保存する。
5. **受け入れ条件（AC）** を書く（次節）。
6. 要約と未決事項を提示し、承認を得たら `Status: approved` にする。

## 受け入れ条件（AC）の書き方

- `AC-1`, `AC-2` … と連番。1 AC = 1 つの観測可能な振る舞い。
- 形式: **Given（前提）/ When（操作）/ Then（結果）**。
- 数値・文言・状態は具体的に。「適切に」「素早く」「など」は禁止。
  - 悪い例: 「入力が不正ならエラーを出す」
  - 良い例: 「Given メールアドレス欄が空 / When 送信ボタンを押す / Then 『メールアドレスを入力してください』が欄の下に表示され、送信は行われない」
- 正常系だけでなく、**異常系・境界値・権限**の AC を必ず含める。
- UI を含む場合は、状態（読み込み中・空・エラー）ごとの表示を AC にする。

## 確認チェックリスト

- [ ] 対象ユーザーと権限（ログイン要否、ロール）
- [ ] 入力の制約（必須/型/長さ/形式）と、不正入力時の挙動
- [ ] 異常系（通信失敗、データなし、重複、競合）の挙動
- [ ] 永続化するデータとその寿命（保存先は ADR が必要か）
- [ ] 非機能（性能の目安、アクセシビリティ、対応ブラウザ）
- [ ] 範囲外（Non-goals）— **やらないことを明記する**
- [ ] 既存機能への影響

## 出力

`docs/specs/NNNN-<slug>.md`（`Status: draft` で作成）。完成後に要約・未決事項・AC 一覧を人間に提示する。
